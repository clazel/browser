# clazel-x509

X.509 certificate decoding, RFC 9525 name matching and the root certificate
table for the Clazel browser. Part of [Clazel](../../README.md), a web browser
whose parsers of untrusted input carry machine-checked proofs. The tier and
its status are in `Cargo.toml` and the
[status table](../../README.md#verification-status); this README covers
the root table, which is plain data and not part of any proof, and the
x509-limbo harness.

## The root table (`roots`)

`roots::ROOTS` is Mozilla's set of trust anchors for TLS servers: one
`Root { label, der, sha256, server_distrust_after }` per root, in the order
of the source file. It is generated by `cargo xtask tables`
(`xtask/src/roots.rs`) into `src/roots/data.rs` from NSS's
`lib/ckfw/builtins/certdata.txt` (MPL-2.0), vendored byte for byte under
`data/nss-0a2b0c75/` (nss-dev/nss commit `0a2b0c75`, 20 October 2026) with its
`SOURCE.md` (URLs, commit, size, SHA-256) and licence. `cargo xtask check`
fails if the vendored file differs from its hash in `SOURCE.md`, if anything
else is in that directory, or if `src/roots/data.rs` differs from what the
generator produces. Nothing is downloaded at build or run time.

At that commit `certdata.txt` holds 169 certificates; the table has **118**.

### Modelling choices

- **Trust bit: server authentication only.** A certificate is in the table
  exactly when its `CKO_NSS_TRUST` object (matched by `CKA_ISSUER` and
  `CKA_SERIAL_NUMBER`) has `CKA_TRUST_SERVER_AUTH CK_TRUST
  CKT_NSS_TRUSTED_DELEGATOR`. The other 51 are left out: 49 are trusted for
  e-mail protection only, and 2 (Go Daddy Class 2 CA, Starfield Class 2 CA)
  are trusted for nothing. No certificate in this file is code-signing-only or
  `CKT_NSS_NOT_TRUSTED`, but the generator handles both (distrusted and
  code-signing-only roots are excluded) and stops on any trust value it does
  not know instead of guessing.
- **`CKA_NSS_SERVER_DISTRUST_AFTER` is carried, not applied.** `None` for
  `CK_FALSE`, otherwise `Some("YYMMDDHHMMSSZ")`, NSS's own `UTCTime` text. At
  this commit one root has a date: Izenpe.com, `260415235959Z`. Roots with a
  date are kept because the date limits which leaf certificates they may
  anchor, not whether the root is a root; deciding that needs the leaf's
  `notBefore`, which is path validation's input, not the table's.
- **Not carried:** `CKA_NSS_EMAIL_DISTRUST_AFTER` (e-mail is out of scope),
  `CKA_NSS_MOZILLA_CA_POLICY`, `CKA_TRUST_STEP_UP_APPROVED`, the e-mail and
  code-signing trust bits, `CKA_SUBJECT`/`CKA_ISSUER`/`CKA_SERIAL_NUMBER`
  (they are in the DER), and the legacy SHA-1 and MD5 hashes.
- **Fingerprint:** `sha256` is computed by the generator (a SHA-256 of its
  own, with the FIPS 180-4 vectors as unit tests, so no dependency is added)
  and must equal the `# Fingerprint (SHA-256)` comment NSS writes above both
  of the certificate's objects, or generation stops.
- **Labels** are NSS's `CKA_LABEL`; they are names for people, not keys. Use
  `sha256` or `der` to identify a root.
- Generation also stops if a certificate has no trust object (or the reverse),
  if the two labels differ, if two certificates share an issuer and serial or
  a DER encoding, or if a DER value is not one SEQUENCE covering its bytes.

### Evidence

`tests/trust_store.rs`: every root decodes with this crate's own decoders
(envelope, TBS, SubjectPublicKeyInfo, extensions, signature algorithms) and is
self-issued; the count, well-known labels and exclusions; no duplicate label,
DER or fingerprint; `ISRG Root X1`'s published fingerprint; `sha256` equals the
system `sha256sum`/`shasum` of `der`; and the table equals `certdata.txt` as
read by a second scanner in the test, which finds the roots through NSS's
fingerprint comments instead of the generator's issuer-and-serial join. The
conformance tier of Phase 3 item 3.5g (a real handshake against a chain to a
table root) is not done here.

### Updating

Follow "Updating" in `data/nss-0a2b0c75/SOURCE.md`: vendor the newer file in a
new `data/nss-<commit>/` directory, point `DATA_DIR` in `xtask/src/roots.rs`
and the `include_str!` and `ROOT_COUNT` in `tests/trust_store.rs` at it, run
`cargo xtask tables`, and commit the result. Review the diff of the table: a
root added to or removed from NSS's trust is a change to what the browser
trusts.

## x509-limbo harness (`tests/conformance_limbo.rs`)

The x509-limbo corpus (C2SP, Apache-2.0; 9,802 testcases, 30,379 distinct
certificates) is vendored byte for byte in `tests/data/x509-limbo/` and reduced
by `cargo xtask testdata` to a testcase index and a binary file of DER
certificates under `tests/generated/` (`cargo xtask check` fails if either is
stale).

What the harness covers:

- Every distinct certificate goes through every decoder (envelope, signature
  algorithm, TBS, SPKI, extensions, SAN, BasicConstraints, KeyUsage,
  ExtendedKeyUsage, NameConstraints, PolicyConstraints) without panicking,
  with the accepted counts pinned.
- **Every `SERVER` testcase with a DNS or IP peer name goes through
  `path::search::exec::verify_server_chain`** (RFC 5280 section 6.1, the
  browser profile and the bounded chain search): limbo's presented chain, its
  trusted certificates as anchors, its validation time (the leaf's notBefore
  when it gives none) and its `max_chain_depth` as `max_intermediates` (6
  when it gives none). Limbo's `SUCCESS` or `FAILURE` is compared with the
  verdict, not the reason. **9,737 of 9,802 testcases agree** (923 `SUCCESS`,
  8,814 `FAILURE`); the other 65 are listed by id, with a reason, in
  `tests/limbo/expected_failures.rs`, and the test fails if an id appears or
  vanishes, if a listed case starts to agree, or if a case that disagrees is
  not listed. (The conformance line reads `pass=9737 xfail=65 fail=0`.)
- None of the certificates of a `SUCCESS` testcase is rejected by a decoder.
- `tests/path_search_limbo.rs` prints the same run by error class and
  family; it pins nothing.

**Signatures are not checked in this crate's run.** The link verifier is a
stand-in that accepts every signature, because the real one
(`CertificateLinks`) is in `clazel-crypto`, which depends on this crate.
That is exact for limbo's `SUCCESS` chains (their signatures are valid) but
means a `FAILURE` that rests on a signature is accepted here. `clazel-crypto`'s
`tests/chain_limbo.rs` runs the signature-related cases with the real links.
Revocation is not checked either (no CRL or OCSP: Phase 8).

The 65 listed testcases, by reason:

| Count | Reason |
|------:|--------|
| 10 | `CLIENT` testcases (client-certificate validation does not exist) |
| 10 | CRL checking (Phase 8) |
| 4 | needs signature verification (3.5f, P11): `invalid::invalid-issuer-key`, the weak-RSA, P-192 and explicit-curve roots |
| 3 | ML-DSA (RFC 9881), not in the algorithm set |
| 1 | `SUCCESS` with no DNS or IP peer name (a directoryName constraint) |
| 3 | deliberate browser-profile refusals of what limbo (RFC 5280 only) accepts: a CA certificate as the target (2), no extKeyUsage on the target (1) |
| 5 | the issuer must include authorityKeyIdentifier or subjectKeyIdentifier (RFC 5280 4.2.1.1, 4.2.1.2): a CA obligation no section 6.1 step reads |
| 3 | the issuer must mark nameConstraints, policyConstraints or a root's basicConstraints critical: section 6.1 processes them whatever the flag |
| 1 | zero serial number (RFC 5280 4.1.2.2) |
| 2 | subjectAltName criticality against the subject (RFC 5280 4.1.2.6, BR 7.1.2.7.12) |
| 6 | CA/Browser Forum rules on a root's contents (BR 7.1.2.1.2, 7.1.2.1.3) |
| 2 | CA/Browser Forum rules on a subscriber's extra or critical extKeyUsage (BR 7.1.2.7.6, 7.1.2.7.10) |
| 9 | CA/Browser Forum rule on the subject commonName (BR 7.1.4.3); the commonName is never read |
| 1 | malformed authorityInfoAccess, a non-critical extension kept opaque |
| 4 | no profile rule on the target's key type or size (BR 6.1.5, p192, DSA, weak RSA, modulus not a multiple of 8) |
| 1 | a root with a 2052-bit RSA key, accepted by the real links as Chrome, Firefox and webpki do according to `clazel-crypto` |

None of the 65 is a known defect of the section 6.1 code. The profile
refusals and the missing profile rules are choices: `src/path/profile.rs`
names each, and whether both browsers refuse the cases of the key-type row
and the zero serial is unconfirmed. Running the whole corpus found no
disagreement that was a bug in the validation, so this work changed no
specification or proof. All 9,572 `bettertls` testcases agree.

## Updating the corpus

See `tests/data/x509-limbo/SOURCE.md`: vendor the new file, run
`cargo xtask testdata`, and the test names every id that appeared or vanished
or changed its verdict.
