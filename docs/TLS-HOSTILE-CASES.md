# TLS hostile-case matrix

This matrix separates parsing/transcript checks, the initial authentication
machine over explicit providers, and future production joins. A message parser
accepting a structure does not mean the negotiated values or peer have been
validated. `tests/auth_state_machine.rs` uses mock validators and input-sensitive
protocol primitives; its tests do not establish real X.509/crypto correctness.

| Hostile case | Exact RFC clause | Expected behavior / alert | Responsible layer | Implemented coverage / gap |
|---|---|---|---|---|
| Unsolicited or duplicated ClientHello; ServerHello before the second ClientHello after HRR; authentication messages before final ServerHello | [RFC 8446 §4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2), [§4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4), [§4.4.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.1) | Reject unexpected message order; protocol endpoint aborts with `unexpected_message`. | Handshake state machine; transcript accumulator enforces only Hello progression. | `transcript_rejects_bad_hello_order_and_preserves_state` in `tests/conformance_key_schedule.rs` and `unsolicited_or_duplicated_hello_messages_are_rejected` / `retry_exchange_requires_exactly_one_second_client_hello` / `retry_exchange_rejects_skipped_key_exchange_messages_without_state_change` in `tests/transcript_adversarial.rs` check transcript rejection/state preservation. `out_of_order_messages_premature_application_and_wrong_ack_are_terminal` also tests authentication-stage ordering and fatal effects; full Hello negotiation remains unimplemented. |
| Second HelloRetryRequest; HRR does not change ClientHello; final ServerHello disagrees with HRR cipher suite or selected version | [RFC 8446 §4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4) | Client aborts second HRR with `unexpected_message`; no-op HRR uses `illegal_parameter`; HRR/ServerHello parameter mismatch uses `illegal_parameter`. | Handshake negotiation and state machine. | `transcript_rejects_bad_hello_order_and_preserves_state` checks second-HRR transcript rejection only. `hello::exec::validate` now rejects second/no-op retries for the fixed TLS 1.3/X25519 profile; `cookie_only_retry_returns_exact_extension_data_and_rejects_invalid_retries` checks both alerts. A maintained negotiation state and actual ClientHello binding remain future work. |
| Retry ClientHello changes a field outside §4.1.2's allowed changes; unoffered retry group/cookie handling | [RFC 8446 §4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2), [§4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4), [§4.2.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.2), [§4.2.8](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.8) | Client must make only the enumerated ClientHello updates; a second HRR is `unexpected_message`. Invalid parameters use the specific rule's alert; RFC 8446 does not define one generic “bad cookie” alert. | Handshake negotiation and extension validation. | `rfc8448_messages` and `rustls_handshake_acceptance` in `tests/conformance_tls_formats.rs` cover encoded HRR/message parsing and differential structural acceptance. `cookie_only_retry_returns_exact_extension_data_and_rejects_invalid_retries` checks exact cookie extension_data and rejects already-offered/unoffered groups. ClientHello2 generation and its unchanged-field invariants remain future work. |
| No common cipher suite or other acceptable security parameters at server | [RFC 8446 §4.1.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.1) | Server aborts with `handshake_failure` or `insufficient_security`. | Server-side negotiation. | No offer/selection state machine; future work. |
| Client receives a cipher suite it did not offer | [RFC 8446 §4.1.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.3) | Client MUST abort with `illegal_parameter`. | Client-side ServerHello validation. | `rejects_invalid_legacy_fields_and_selected_version` checks rejection of an unoffered cipher for the fixed 0x1303 profile; binding that profile to a generated ClientHello remains future work. |
| Client receives an invalid selected version | [RFC 8446 §4.2.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.1), [Appendix D.1](https://www.rfc-editor.org/rfc/rfc8446#appendix-D.1) | An unoffered version, or a version before TLS 1.3, in ServerHello's `supported_versions` requires `illegal_parameter`. An unsupported or unacceptable older version selected through legacy negotiation requires `protocol_version`. | Client-side version negotiation. | `rejects_invalid_legacy_fields_and_selected_version` checks selected-version rejection and requires ignoring legacy_version when supported_versions is present. This profile offers only TLS 1.3; legacy-version negotiation is not implemented. |
| Server sends an unsolicited extension response (outside the HRR cookie exception), a recognized extension in a prohibited message, or omits a mandatory extension | [RFC 8446 §4.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2), [§6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2) | Unsolicited response: `unsupported_extension`. Recognized extension in a prohibited message: `illegal_parameter`. Missing mandatory extension: `missing_extension`. | Handshake extension validation. | `hand_built_error_rules` and `rustls_handshake_acceptance` in `tests/conformance_tls_formats.rs` cover duplicate/malformed extension structures and selected parser comparisons. Recognized-extension placement is checked by the existing parser; `auth::exec::Auth` checks EE responses against its captured offers, tested by `malformed_requests_unoffered_extensions_and_signature_schemes_are_rejected`; binding those captured offers to a real ClientHello is the future Hello join. |
| TLS 1.3-capable client negotiates TLS 1.2 or below and the ServerHello random ends in a downgrade sentinel | [RFC 8446 §4.1.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.3) | Client MUST check the final 8 random bytes; presence of either sentinel (`DOWNGRD\x01` for TLS 1.2 or `DOWNGRD\x00` for TLS 1.1 and below) requires abort with `illegal_parameter`. The server sets the relevant sentinel when negotiating the older version. | Client-side downgrade detection; server random generation. | No downgrade sentinel validation or handshake test. |
| Record exceeds plaintext or ciphertext limit; invalid protected record authentication | [RFC 8446 §§5.1](https://www.rfc-editor.org/rfc/rfc8446#section-5.1), [5.2](https://www.rfc-editor.org/rfc/rfc8446#section-5.2) | Oversized record: terminate with `record_overflow`; failed record authentication: `bad_record_mac`. | Record parser and AEAD record layer. | `hand_built_error_rules` in `tests/conformance_tls_formats.rs` tests record length boundaries and alert mapping; protected record vectors are exercised by `rfc8448_records`. Integrated traffic-key record protection remains future work. |
| ChangeCipherSpec has invalid contents, appears interleaved, or is accepted outside compatibility-mode conditions | [RFC 8446 §5](https://www.rfc-editor.org/rfc/rfc8446#section-5), [Appendix D.4](https://www.rfc-editor.org/rfc/rfc8446#appendix-D.4) | A valid dummy CCS is ignored only under the compatibility rules; other unexpected CCS use terminates with `unexpected_message`. | Record protocol and handshake state machine. | `hand_built_error_rules` and `rustls_alerts_and_change_cipher_spec` in `tests/conformance_tls_formats.rs` cover contents, interleaving and parser behavior. Full handshake-phase acceptance is future work. |
| Finished has incorrect verify_data length or incorrect MAC | [RFC 8446 §§4.4.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.4), [6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2) | Wrong fixed length is a syntax/length error: `decode_error`. Correct-length but incorrect verify_data is failed verification: `decrypt_error`. | Handshake parser and authentication/key schedule. | `hand_built_error_rules` in `tests/conformance_tls_formats.rs` checks wrong length against `HASH_LEN` (32 for SHA-256) returns `Decode`; `rfc8448_key_schedule` and `transcript_accumulator_matches_rfc8448` in `tests/conformance_key_schedule.rs` cover valid vectors. `malformed_and_incorrect_server_finished_fail_with_distinct_alerts` checks authentication MAC comparison and fatal failure over explicit Crypto/Verifier parameters; the production provider is not joined. |
| CertificateVerify signature fails verification | [RFC 8446 §4.4.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.3) | Receiver MUST terminate with `decrypt_error`. | Handshake authentication and signature provider. | `certificate_verify_input_matches_rfc8446_section_4_4_3` checks constructed signature input. `certificate_verify_checks_captured_identity_and_fails_closed` checks invocation with the validated leaf key and exact server transcript input and fatal rejection by a mock signature provider; production verification is not joined. |
| Certificate is malformed, lacks a trusted path, expired, or outside its validity period | [RFC 8446 §4.4.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.2), [§6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2), [RFC 5280 §6.1](https://www.rfc-editor.org/rfc/rfc5280#section-6.1) | Depending on the failure: `decode_error` for malformed TLS Certificate framing; `unknown_ca` when no trusted CA can be located/matched; `certificate_expired` if expired or not currently valid; otherwise the applicable certificate alert. | Generic DER decoder exists in `clazel-der`; X.509 certificate decoding and path validation are future work. | `rfc8448_messages` and `rustls_handshake_acceptance` cover TLS Certificate message framing/structure only. `typed_chain_failures_and_empty_chain_preserve_expected_alerts` checks empty-chain rejection and typed validator errors; no production X.509 certificate decoder or path validator is joined. |
| Certificate identity does not match the requested DNS name | [RFC 9525 §6](https://www.rfc-editor.org/rfc/rfc9525#section-6) | Client terminates the connection with a bad-certificate error; the RFC does not specify a universal TLS alert mapping for this client-side result. | Endpoint identity policy after certificate path validation. | The authentication machine binds the configured host/time to its validator call; no production X.509 name matcher is joined. |
| Certificate revocation status is not checked | [RFC 8446 Appendix C.2](https://www.rfc-editor.org/rfc/rfc8446#appendix-C.2) | Revocation support is discussed by the RFC; this repository's phase plan explicitly defers CRL/OCSP checking to Phase 8. | Future revocation/OCSP/CRL work; not a Phase 3 exit criterion. | No revocation checks. |

The test-only transcript provider returns a fixed SHA-256-sized digest solely
to exercise the synthetic `message_hash` path. It is not cryptographic test
evidence. Transcript `phase` and `retried` describe sequencing only; neither
indicates peer authentication.
