# TLS hostile-case matrix

This matrix separates parsing/transcript checks, the initial authentication
machine over explicit providers, and future production joins. A message parser
accepting a structure does not mean the negotiated values or peer have been
validated. `tests/auth_state_machine.rs` uses mock validators and input-sensitive
protocol primitives; its tests do not establish real X.509/crypto correctness.

| Hostile case | Exact RFC clause | Expected behavior / alert | Responsible layer | Implemented coverage / gap |
|---|---|---|---|---|
| Unsolicited or duplicated ClientHello; ServerHello before the second ClientHello after HRR; authentication messages before final ServerHello | [RFC 8446 §4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2), [§4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4), [§4.4.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.1) | Reject unexpected message order; protocol endpoint aborts with `unexpected_message`. | Handshake state machine; transcript accumulator enforces only Hello progression. | `transcript_rejects_bad_hello_order_and_preserves_state` in `tests/conformance_key_schedule.rs` and `unsolicited_or_duplicated_hello_messages_are_rejected` / `retry_exchange_requires_exactly_one_second_client_hello` / `retry_exchange_rejects_skipped_key_exchange_messages_without_state_change` in `tests/transcript_adversarial.rs` check transcript rejection/state preservation. `out_of_order_messages_premature_application_and_wrong_ack_are_terminal` tests authentication-stage ordering; `connection_dispatch.rs` now covers record-level authentication order and exact client-flight acknowledgement. |
| Second HelloRetryRequest; HRR does not change ClientHello; final ServerHello disagrees with HRR cipher suite or selected version | [RFC 8446 §4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4) | Client aborts second HRR with `unexpected_message`; no-op HRR uses `illegal_parameter`; HRR/ServerHello parameter mismatch uses `illegal_parameter`. | Handshake negotiation and state machine. | `transcript_rejects_bad_hello_order_and_preserves_state` checks second-HRR transcript rejection only. `hello::exec::validate` now rejects second/no-op retries for the fixed TLS 1.3/X25519 profile; `cookie_only_retry_returns_exact_extension_data_and_rejects_invalid_retries` checks both alerts. `rejects_wrong_session_echo_repeated_retry_and_oversized_cookie` exercises the owned controller's retained session/retry state. |
| Retry ClientHello changes a field outside §4.1.2's allowed changes; unoffered retry group/cookie handling | [RFC 8446 §4.1.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2), [§4.1.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.4), [§4.2.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.2), [§4.2.8](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.8) | Client must make only the enumerated ClientHello updates; a second HRR is `unexpected_message`. Invalid parameters use the specific rule's alert; RFC 8446 does not define one generic “bad cookie” alert. | Handshake negotiation and extension validation. | `rfc8448_messages` and `rustls_handshake_acceptance` in `tests/conformance_tls_formats.rs` cover encoded HRR/message parsing and differential structural acceptance. `cookie_only_retry_returns_exact_extension_data_and_rejects_invalid_retries` checks exact cookie extension_data and rejects already-offered/unoffered groups. `cookie_retry_echoes_cookie_and_preserves_client_hello_offers` checks generated CH2, unchanged fields/extensions and the complete rewritten transcript; the 4098-byte cookie extension_data cap is a documented resource policy. |
| No common cipher suite or other acceptable security parameters at server | [RFC 8446 §4.1.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.1) | Server aborts with `handshake_failure` or `insufficient_security`. | Server-side negotiation. | No offer/selection state machine; future work. |
| Client receives a cipher suite it did not offer | [RFC 8446 §4.1.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.3) | Client MUST abort with `illegal_parameter`. | Client-side ServerHello validation. | `rejects_invalid_legacy_fields_and_selected_version` checks rejection of an unoffered cipher for the fixed 0x1303 profile; `start_emits_the_fixed_client_profile_and_respects_sni_choice` checks that generated ClientHello actually offers that profile. |
| Client receives an invalid selected version | [RFC 8446 §4.2.1](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.1), [Appendix D.1](https://www.rfc-editor.org/rfc/rfc8446#appendix-D.1) | An unoffered version, or a version before TLS 1.3, in ServerHello's `supported_versions` requires `illegal_parameter`. An unsupported or unacceptable older version selected through legacy negotiation requires `protocol_version`. | Client-side version negotiation. | `rejects_invalid_legacy_fields_and_selected_version` checks selected-version rejection and requires ignoring legacy_version when supported_versions is present. This profile offers only TLS 1.3; legacy-version negotiation is not implemented. |
| Server sends an unsolicited extension response (outside the HRR cookie exception), a recognized extension in a prohibited message, or omits a mandatory extension | [RFC 8446 §4.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2), [§6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2) | Unsolicited response: `unsupported_extension`. Recognized extension in a prohibited message: `illegal_parameter`. Missing mandatory extension: `missing_extension`. | Handshake extension validation. | `hand_built_error_rules` and `rustls_handshake_acceptance` in `tests/conformance_tls_formats.rs` cover duplicate/malformed extension structures and selected parser comparisons. Recognized-extension placement is checked by the existing parser; `auth::exec::Auth` checks EE responses against its captured offers, tested by `malformed_requests_unoffered_extensions_and_signature_schemes_are_rejected`; `hello::client` now generates those offers and `hello::join` transfers them into authentication, including any retry cookie. `lemma_offer_binding` states that correspondence. |
| TLS 1.3-capable client negotiates TLS 1.2 or below and the ServerHello random ends in a downgrade sentinel | [RFC 8446 §4.1.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.3) | Client MUST check the final 8 random bytes; presence of either sentinel (`DOWNGRD\x01` for TLS 1.2 or `DOWNGRD\x00` for TLS 1.1 and below) requires abort with `illegal_parameter`. The server sets the relevant sentinel when negotiating the older version. | Client-side downgrade detection; server random generation. | No downgrade sentinel validation or handshake test. |
| X25519 agreement fails or yields an all-zero shared secret; private scalar does not match the public share sent | [RFC 8446 §7.4.2](https://www.rfc-editor.org/rfc/rfc8446#section-7.4.2), [§4.2.8.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.8.2) | Reject a failed/all-zero derived secret before traffic-key derivation (this profile chooses `illegal_parameter`); local key mismatch uses `internal_error`. | Parameterized Hello-to-authentication join; production X25519 is not implemented. | `rejects_private_key_not_bound_to_client_share_before_agreement`, `rejects_provider_failure_and_all_zero_derived_secret`, and `binds_exact_private_and_peer_inputs_and_derives_secrets_from_peer_result` check mock-provider decisions and exact inputs; `joined_secrets_drive_mock_authentication_and_finished_transcript` exercises both Finished messages with independently calculated test-double secrets. |
| Record exceeds plaintext or ciphertext limit; invalid protected record authentication | [RFC 8446 §§5.1](https://www.rfc-editor.org/rfc/rfc8446#section-5.1), [5.2](https://www.rfc-editor.org/rfc/rfc8446#section-5.2) | Oversized record: terminate with `record_overflow`; failed record authentication: `bad_record_mac`. | Record parser, AEAD record layer, and connection dispatcher. | `hand_built_error_rules` in `tests/conformance_tls_formats.rs` tests record length boundaries and alert mapping; protected record vectors are exercised by `rfc8448_records`. `tamper_reorder_ccs_and_malformed_inner_plaintext_are_terminal` checks epoch failure. `wrong_finished_and_bad_mac_fail_closed` checks the dispatcher drops all state after a bad MAC and cannot restart. |
| Record sequence reuse, wrap, premature advancement or wrong-direction key installation | [RFC 8446 §5.3](https://www.rfc-editor.org/rfc/rfc8446#section-5.3), [§7.3](https://www.rfc-editor.org/rfc/rfc8446#section-7.3) | Start each key/direction at zero, increment once per successful record, rekey or terminate before wrap. A partial prefix consumes no counter. Client handshake secret sends; server handshake secret receives. | Owned traffic epochs and connection dispatcher. | `derives_key_and_iv_and_uses_nonce_sequence_and_header_ad`, `incomplete_input_does_not_call_aead_or_advance_counter`, and `hello_record_auth_handoff_installs_directional_keys_and_processes_ee` check independent reference keys/nonces, consumed-prefix lengths and direction binding. `fragmented_server_flight_gates_client_finished_and_application_keys` checks handshake-to-application key installation after the exact client-flight acknowledgement. `traffic::lemmas::lemma_advance` and concrete u64::MAX mutation witnesses cover exhaustion without a test-only counter setter. |
| ChangeCipherSpec has invalid contents, appears interleaved, or is accepted outside compatibility-mode conditions | [RFC 8446 §5](https://www.rfc-editor.org/rfc/rfc8446#section-5), [Appendix D.4](https://www.rfc-editor.org/rfc/rfc8446#appendix-D.4) | A valid unprotected dummy CCS is dropped during the handshake before peer Finished; unexpected, malformed, or protected CCS use terminates with `unexpected_message` or the record parser's specific alert. | Record protocol and connection dispatcher. | `hand_built_error_rules` and `rustls_alerts_and_change_cipher_spec` in `tests/conformance_tls_formats.rs` cover contents and parser behavior. `finished_must_end_at_record_boundary_and_compatibility_ccs_is_dropped` checks a dummy CCS before the server flight and rejects it after the client flight is acknowledged. |
| Finished has incorrect verify_data length or incorrect MAC; Finished is followed by more handshake data in the same record | [RFC 8446 §§4.4.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.4), [§5.1](https://www.rfc-editor.org/rfc/rfc8446#section-5.1), [§6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2) | Wrong fixed length is a syntax/length error: `decode_error`. Correct-length but incorrect verify_data is failed verification: `decrypt_error`. Data after server Finished before the key change is an unexpected handshake message and aborts. | Handshake parser, authentication machine, and connection dispatcher. | `malformed_and_incorrect_server_finished_fail_with_distinct_alerts` checks the authentication errors; `wrong_finished_and_bad_mac_fail_closed` checks authenticated record processing and terminal state; `finished_must_end_at_record_boundary_and_compatibility_ccs_is_dropped` checks that Finished must be the last complete message at the record boundary. |
| CertificateVerify signature fails verification | [RFC 8446 §4.4.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.3) | Receiver MUST terminate with `decrypt_error`. | Handshake authentication and signature provider. | `certificate_verify_input_matches_rfc8446_section_4_4_3` checks constructed signature input. `certificate_verify_checks_captured_identity_and_fails_closed` checks invocation with the validated leaf key and exact server transcript input and fatal rejection by a mock signature provider; production verification is not joined. |
| Certificate is malformed, lacks a trusted path, expired, or outside its validity period | [RFC 8446 §4.4.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.2), [§6.2](https://www.rfc-editor.org/rfc/rfc8446#section-6.2), [RFC 5280 §6.1](https://www.rfc-editor.org/rfc/rfc5280#section-6.1) | Depending on the failure: `decode_error` for malformed TLS Certificate framing; `unknown_ca` when no trusted CA can be located/matched; `certificate_expired` if expired or not currently valid; otherwise the applicable certificate alert. | Generic DER decoder exists in `clazel-der`; X.509 certificate decoding and path validation are future work. | `rfc8448_messages` and `rustls_handshake_acceptance` cover TLS Certificate message framing/structure only. `typed_chain_failures_and_empty_chain_preserve_expected_alerts` checks empty-chain rejection and typed validator errors; no production X.509 certificate decoder or path validator is joined. |
| Certificate identity does not match the requested DNS name or IP address | [RFC 9525 §6](https://www.rfc-editor.org/rfc/rfc9525#section-6) | Client terminates the connection with a bad-certificate error; the RFC does not specify a universal TLS alert mapping for this client-side result. | Endpoint identity policy after certificate path validation. | `clazel-x509::matcher` implements DNS/IP identity matching separately, with `rfc9525_dns_case_and_wildcard_examples`, `malformed_wildcards_and_names_are_rejected`, `ip_ids_are_binary_and_exact`, and `dns_and_ip_identifiers_never_cross_match`. The TLS verifier still does not join this matcher to a validated certificate path. |
| Certificate revocation status is not checked | [RFC 8446 Appendix C.2](https://www.rfc-editor.org/rfc/rfc8446#appendix-C.2) | Revocation support is discussed by the RFC; this repository's phase plan explicitly defers CRL/OCSP checking to Phase 8. | Future revocation/OCSP/CRL work; not a Phase 3 exit criterion. | No revocation checks. |
| Fragmented or coalesced protected records; partial input or an unconsumed suffix | [RFC 8446 §5.1](https://www.rfc-editor.org/rfc/rfc8446#section-5.1) | Buffer an incomplete record, process exactly one complete record prefix, and leave any following bytes with the caller. | Bounded record framer and connection dispatcher. | Framer unit tests check every split point; `fragmented_server_flight_gates_client_finished_and_application_keys` fragments a protected record, and `finished_must_end_at_record_boundary_and_compatibility_ccs_is_dropped` resubmits suffixes from coalesced records. |
| KeyUpdate changes direction keys, responds to update_requested with KeyUpdate(0), or arrives fragmented/coalesced | [RFC 8446 §4.6.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.6.3), [§7.2](https://www.rfc-editor.org/rfc/rfc8446#section-7.2) | Derive the next secret with `traffic upd`; peer receive keys rotate immediately, local send keys rotate only after the exact update flight is acknowledged. A requested update requires a response with request_update=0; no application data is sent while that response awaits acknowledgement. | Connection dispatcher and traffic epochs. | `local_key_update_waits_for_exact_send_ack_and_rotates_only_client_epoch` checks the exact-send gate, wrong acknowledgement failure, request bit, and fresh send epoch. `peer_key_update_rotates_receive_epoch_and_sends_unrequested_response` checks independent directional rotation and response bit 0. `fragmented_key_update_with_trailing_message_is_rejected` checks reassembly and rejects more than one post-handshake message in a record. |
| `user_canceled` alert received | [RFC 8446 §6](https://www.rfc-editor.org/rfc/rfc8446#section-6), [§6.1](https://www.rfc-editor.org/rfc/rfc8446#section-6.1) | `user_canceled` is a closure alert, generally warning-level, and SHOULD be followed by `close_notify`. | Connection dispatcher. | Gap: the current dispatcher treats every alert except `close_notify` as fatal; `user_canceled` behavior is not implemented or tested. |
| Application plaintext arrives before server authentication or before client-flight send acknowledgement | [RFC 8446 §§4.4.4](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.4), [§5.2](https://www.rfc-editor.org/rfc/rfc8446#section-5.2) | Do not release application data until server Finished is verified and the exact client flight is acknowledged; an application record in the handshake phase aborts with `unexpected_message`. | Authentication machine and connection dispatcher. | `application_record_before_server_finished_is_terminal` checks the early protected application record; `fragmented_server_flight_gates_client_finished_and_application_keys` checks the send acknowledgement, fresh application epochs, and subsequent application delivery. |

The test-only transcript provider returns a fixed SHA-256-sized digest solely
to exercise the synthetic `message_hash` path. It is not cryptographic test
evidence. Transcript `phase` and `retried` describe sequencing only; neither
indicates peer authentication.
