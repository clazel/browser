# Phase 9: a proven JIT, JavaScript first, detailed plan

**Status: proposed (2026-11-16). Nothing is built. Item 9.0's decisions are
open, and 9.0(c) changes CLAUDE.md rule 1, which only the maintainer can
decide.** Phase 7 (the interpreter) is not planned in detail yet either; this
plan lists what Phase 7 must fix in place for the JIT to be possible (item
9.1), so that work is done once.

**Goal:** JavaScript runs as machine code the browser generated. One
property is proven before anything runs: generated code cannot touch memory
outside the regions it was handed, and cannot jump anywhere but its own
instructions and its one exit. A second property is proven op by op: the code
does what the interpreter would have done. The machine-code half of the work
is built so that a WebAssembly front end can reuse it unchanged (see
"Looking ahead: WebAssembly"). WebAssembly itself is not in this phase.

*Exit:* on macOS arm64 and Linux aarch64, a page's hot functions run through
the baseline JIT. Every code blob passes the tier 2 validator before it is
mapped executable. The JS conformance suite (Test262, as Phase 7 vendors it)
gives the same results with the JIT on and off. A stated set of benchmarks
is measured against the interpreter and the result is reported, not
asserted. On x86-64 the browser still interprets, and the README says so.

Nothing in this phase speculates on types, inlines across functions,
allocates registers globally or patches code it has already validated. An
optimizing tier is future work ("Looking ahead"). This phase only makes the
**baseline** tier fast and proven: no dispatch loop, with fast paths for
small integers and property loads through inline caches.

A convention for this file, as in phase-5.md: a section number marked † was
written from memory, not read at a pinned commit. It must be checked against
the commit a spec header pins before that header cites it.

## Why this shape

A proven optimizing JIT for JavaScript is a research problem. A machine-checked
proof covers speculation and deoptimization only for toy languages (CoreJIT,
Barrière et al., POPL 2021). Production JITs have proven pieces, such as range
analysis (Vera) and CacheIR code generators (Icarus), not the whole. Two
results show what is achievable now:

- **Validating the output instead of proving the compiler** (NaCl's
  validator; VeriWasm, NDSS 2021). A small checker reads every blob of
  generated code and refuses it unless it stays inside its sandbox. Memory
  safety then depends on the checker, not on the compiler. That is how this
  repository already works: trust a small proven thing, not a large clever one.
- **Per-template proofs for a non-optimizing JIT** (Jitk, OSDI 2014;
  Jitterbug, OSDI 2020, for the Linux BPF JITs). Each bytecode op lowers to
  a fixed instruction sequence, and each sequence is proven to simulate its
  op. Composition is then one lemma.

So this phase has two layers, and they ship in this order:

1. **Safety (tier 2, required before any generated byte runs):** the
   validator. It makes the one `unsafe` call into generated code sound,
   whatever the compiler does.
2. **Correctness (target tier 2, may trail the code):** the front end and the
   back end refine the bytecode semantics. A gap here is a wrong answer
   inside the page's own sandbox, never a memory error. It is listed as such
   until it is proven.

## Exit criteria

Phase 9 is done when all of these hold:

1. **Tiers:**
   - `clazel-a64` (the A64 instruction-set spec, encoder and decoder) and
     `clazel-codecheck` (the validator) at **tier 2**, with mutations,
     conformance and an independent transcription each.
   - `clazel-lir` (the low-level IR and its semantics) at **tier 2**.
   - `clazel-jit` (back end and JS front end) at **tier 2** if 9.8 and 9.9's
     proofs went through. Otherwise it stays at its real tier, and the README
     says which ops are proven.
2. **The validator's theorem** (9.5), stated over `clazel-a64`'s semantics:
   every execution of an accepted blob, started at an accepted entry with the
   context invariant, only loads and stores inside the regions it was handed
   and leaves only through the exit stub. It has no system instruction, does
   not touch the reserved registers or the stack pointer except in the fixed
   prologue and epilogue, and never runs past its end.
3. **ISA evidence** (9.3): `clazel-a64`'s semantics is transcribed from Arm's
   machine-readable specification, and then transcribed again independently,
   with the two proven equal on the subset. Running every instruction
   template on real hardware, over generated and boundary inputs, matches the
   spec's result bit for bit (macOS arm64 runner, Linux aarch64 runner).
4. **Suites:** Test262 with the JIT forced on for every function (a
   `--jit=always` flag) gives exactly the interpreter's results, with
   failures listed by name.
5. **Sandbox** (9.7): the renderer never has a page that is both writable and
   executable. On Linux, seccomp argument filters enforce that `mmap` and
   `mprotect` add `PROT_EXEC` only on the code region. macOS uses `MAP_JIT`
   with the per-thread write-protect switch and the `allow-jit` entitlement.
   Windows keeps `PROHIBIT_DYNAMIC_CODE` and the JIT stays off there (9.0(e)).
6. **Hostile tests:**
   - blobs assembled by hand to escape (out-of-region loads, computed jumps
     into the middle of instructions, `svc`, writes to the context register,
     self-modification) are all refused;
   - a fuzzer that mutates accepted blobs finds no accepted blob that faults
     outside its regions when run under a guard-page harness.
7. `scripts/verify.sh` exits 0 and CI's full verification is green. Every
   `clazel-sys` change has an audit row by another session (rule 1).

## What is proven, and what is assumed

1. **Proven (Verus):**
   - the A64 encoder and decoder are inverses on the subset;
   - the validator's theorem (exit criterion 2);
   - LIR's semantics is deterministic, and its typing rules hold;
   - per op, the JS front end's lowering refines the bytecode `step`
     (Phase 7's spec);
   - per LIR instruction, the back end's code refines LIR's semantics;
   - composition: a whole function's code refines the bytecode semantics run
     on that function.
2. **Assumed, and listed in VERIFICATION.md's TCB:**
   - the A64 semantics is faithful to the hardware for the instructions the
     validator accepts. The evidence is the independent transcription and
     the hardware differential tests, not a proof;
   - the enter stub in `clazel-sys` (9.6), its audit and its tests;
   - the OS honours page protections, with W^X as set;
   - the cache-maintenance sequence (`dc cvau`, `ic ivau`, `isb`, done by the
     OS call on macOS and by our stub on Linux) makes new code visible.
3. **Not covered, and said so:**
   - Spectre-style speculation. A blob that is architecturally confined can
     still leak its own process's memory through a side channel. The defence
     is the existing process-per-site model: the renderer holds only its own
     site's data, and the kernel enforces that whatever the renderer does.
   - Timing and performance.
   - Correctness of any op the README lists as unproven.

## Design choices that keep WebAssembly in mind

Each choice below is made for JS and also makes a Wasm front end a small
addition rather than a second JIT.

- **One low-level IR, LIR, shaped like Wasm.**
  - Control flow is structured (`block`, `loop`, `if`, `br`, `br_if`,
    `br_table`) with no arbitrary goto.
  - Values are typed `i32`, `i64`, `f64` (and later `f32`).
  - Memory is accessed only through **regions**, each with a base and a
    bound, and every access names its region.

  A JS op lowers to a short LIR sequence, and a Wasm instruction lowers
  almost one to one. Structured control flow also makes the validator's
  control-flow check simple, because every jump target is known when the
  code is emitted.
- **Regions are the only memory.** A blob is entered with a context register
  pointing at a fixed table of (base, bound) pairs:
  - JS: the value stack (frames), the object arena, the inline-cache data and
    the constant pool;
  - Wasm later: linear memory, globals and tables.

  Every load and store is `base + checked index`, with an explicit bounds
  check. There are no guard-page tricks, so a proof never relies on a
  4 GiB reservation and memory64 costs nothing extra. Indexes are masked
  after the check, which also blunts Spectre v1 within a region.
- **Generated code never calls anything.** A runtime service (allocation,
  a slow property path, a GC point, a call to a native DOM function, and for
  Wasm a host call, `memory.grow` or a trap) is an **exit**. The code stores
  an exit code and its operands in the context and returns to the enter stub.
  Rust does the work and re-enters at a recorded resume point. So Rust is
  never called from generated code: no callbacks, no function pointers to
  Rust, and no unwinding through generated frames. Regions are passed afresh
  at each entry, so the arena may grow or move between entries. JS
  exceptions and Wasm traps take the same path.
- **Code is immutable once validated.** Inline caches are **data** (shape id,
  slot index) in a region that the code reads. There is no stub patching, so
  each blob is validated exactly once. Wasm needs no patching either.
- **The JIT's frames are the interpreter's frames.** JS frames live in a
  value-stack region with the layout Phase 7's interpreter uses. Baseline
  code keeps every bytecode register in its slot at op boundaries. Moving
  between interpreter and JIT, either way, is then a jump with no state
  translation. That covers on-stack replacement, an exception, and
  "this op is not compiled". JS-to-JS calls push frames in the region and
  never use the native stack, so the native stack depth of an entry is a
  constant the validator checks. Wasm frames use the same region the same
  way.
- **Values are one `u64` (NaN-boxed)** with heap references as arena
  indexes (9.1). JS and Wasm then share LIR's `i64` and `f64` types, and a
  JS↔Wasm boundary converts values without allocating.
- **The instruction-set layer knows nothing of JS.** `clazel-a64`,
  `clazel-codecheck`, `clazel-lir` and the back end take no JS-specific type.
  `cargo xtask check` can enforce that through their dependency lists.

## Work items

### 9.0 Decisions for the maintainer (S): open

**(a) The first instruction set.**
- **A: A64 first** (macOS arm64, Linux aarch64). Instructions are a fixed 4
  bytes, so the decoder is total and there are no overlapping instruction
  streams. Arm publishes a machine-readable specification to transcribe from,
  and CI already has a macOS arm64 runner for the hardware tests.
- **B: x86-64 first.** Linux x86-64 is CI's main platform and has more
  desktop users. But instructions vary in length, so the validator needs
  NaCl-style aligned bundles to rule out jumps into the middle of an
  instruction, and the semantics to transcribe is far larger.

**Recommendation: A.** x86-64 follows as a second `clazel-x64` crate behind
the same LIR, with its own validator theorem.

**(b) Where the validator runs.**
- **V1: in the renderer.** It is simple and fast. A renderer bug cannot
  bypass it, because outside generated code everything is safe Rust, so the
  only way to run arbitrary code is through a blob that was validated.
- **V2: in a separate code process that maps code into the renderer.** This
  was Edge's out-of-process JIT. The renderer keeps no right to make memory
  executable, so `PROHIBIT_DYNAMIC_CODE` and seccomp could forbid
  `PROT_EXEC` there entirely. The cost is a process, IPC per blob, and a
  `clazel-sys` change to map memory across processes.

**Recommendation: V1 now, V2 as the Windows path (e).**

**(c) The `unsafe` rule for entering generated code** (CLAUDE.md rule 1 and
`xtask/src/sys.rs` rule 8). Today every call through a function pointer is
rejected, except a dispatcher cast or a vtable slot. Entering a blob needs
exactly one more form.
- **E1:** one new category, the **code entry**. It is exactly one function in
  `clazel-sys`, `enter(region: &CodeRegion, entry: Validated, ctx: &mut
  Context) -> Exit`. It holds one `unsafe` block, which turns the region's
  base address plus the validated offset into an `extern "C" fn(*mut u64) ->
  u64` and calls it. A `Validated` value can be built only by
  `clazel-codecheck`'s `check`, so the policy decision stays in verified
  code, as rule 1 requires. Its `SAFETY:` comment cites the validator's
  theorem, the A64 procedure call standard (AAPCS64) and the OS's W^X
  documentation. `xtask/src/sys.rs` learns the one allowed shape, and the
  audit must check it.
- **E2:** the same, but the stub is a fixed blob of machine code shipped as
  data and validated like any other. The `unsafe` then calls only that stub,
  and the stub jumps to the target. It is no smaller in substance, and it
  adds a trusted blob.

**Recommendation: E1.** Changing rule 1 is the maintainer's decision, and
the first `clazel-sys` change under it is audited by another session.

**(d) Which tier gates shipping.**
- **G1:** the JIT is on by default once the validator is tier 2, with
  correctness proofs following op by op. An op that is not proven yet still
  passes Test262 with the JIT forced on, and the README lists it.
- **G2:** off by default until `clazel-jit` reaches tier 2.

**Recommendation: G1.** Memory safety is the property the rest of the
browser promises, and the validator gives it from day one.

**(e) Windows.** The JIT stays off there, and `PROHIBIT_DYNAMIC_CODE` stays
on, until (b) V2 exists. Turning the mitigation off would weaken every
renderer for a performance gain. **Recommendation: keep it off.**

### 9.1 What Phase 7 must fix in place (S, a constraint on Phase 7)

These are written into phase-7.md when it is planned:
- the bytecode semantics is a Verus `spec fn step`, defined before the
  interpreter, which refines it;
- register-based bytecode, with frames in one value-stack region of `u64`
  slots;
- NaN-boxed values, with heap references as `u32` arena indexes;
- inline caches as data, keyed by a shape id;
- every operation that can allocate, call out or throw is a distinguished
  op, so it maps to an exit.

The interpreter stays at Phase 7's tier. Only `step` must be a spec.

### 9.2 Test data and baselines (S)

- Pin Arm's machine-readable A64 specification (its release and checksum)
  and the Sail Arm model, which is used only for the independent
  transcription.
- Pin the benchmark set, and record the interpreter's numbers.
- Make Test262 runnable with `--jit=always`.

### 9.3 `clazel-a64`: spec and contracts, then encoder, decoder and proofs (L)

- The subset: integer arithmetic and logic, shifts, compare and conditional
  select, loads and stores (register base plus scaled register or immediate
  offset), `b`, `b.cond`, `cbz`/`cbnz`, `br`/`blr` only for the fixed exit,
  `ret`, `fadd`/`fsub`/`fmul`/`fdiv`/`fsqrt`, `fcmp`, `fcvt*`/`scvtf`, and
  moves between general and FP registers.
- Semantics as a `spec fn` over a machine state: registers, flags, PC, and a
  memory given as a partial map. A memory access outside the map is a stuck
  state, which the validator's theorem rules out.
- Contracts first (rule 3). Then the encoder and decoder, proven inverse.
- Independent transcription from the Sail model, proven equal on the subset.
- Differential tests on hardware: each instruction run over boundary values
  and generated values, compared with the spec.

### 9.4 `clazel-lir`: syntax, typing, semantics (M)

- Structured control flow, typed values, region-tagged loads and stores
  with explicit `bounds_check`, and `exit(code, operands)`.
- A `spec fn` big-step semantics, and a typing judgment proven sound
  (well-typed programs don't get stuck, except at an exit or a trap).
- Built to be the target of a Wasm front end: the instruction list is
  checked against the Wasm core instructions it would need, and gaps are
  recorded.

### 9.5 `clazel-codecheck`: the validator (L)

- Input: code bytes, an entry list and a region table layout. Output:
  `Validated` entries, or a refusal with a reason.
- Checks, in one linear pass:
  - every word decodes to an instruction in the subset;
  - every direct branch target is an instruction in the blob;
  - there is no indirect branch except the fixed exit sequence;
  - every load and store uses a region base register plus an index register
    that was compared against that region's bound, and masked, earlier in
    the same basic block, by a fixed recognizable sequence;
  - the reserved registers (context, region bases) and `sp` are written only
    in the fixed prologue and epilogue;
  - no system instruction, no exclusive or atomic op (yet), and no literal
    pool;
  - every path ends in the exit sequence or a branch.
- The theorem (exit criterion 2), proven over `clazel-a64`'s semantics, for
  every number of steps.
- Independent transcription: a second validator written as a dataflow
  analysis, proven to accept only what the first accepts.
- Hostile corpus and mutation fuzzer (exit criterion 6).

### 9.6 `clazel-sys`: code region, W^X, enter (M, after 9.0(c))

- Linux: `mmap` RW, write, then `mprotect` to RX after validation, with the
  cache maintenance done by our stub's validated prologue or by
  `__builtin___clear_cache`-equivalent instructions emitted in Rust.
- macOS: `MAP_JIT`, `pthread_jit_write_protect_np` and
  `sys_icache_invalidate`.
- `enter` per 9.0(c). Tests skip under Miri, as other foreign calls do.
- The session that writes this item does not write its audit row.

### 9.7 Sandbox (M)

- seccomp argument filters: `PROT_EXEC` is allowed only on the code region's
  fixed address range, which is reserved before the filter goes on.
- Seatbelt adds the JIT entitlement; the process tests extend to it.
- `appcontainer.rs`: unchanged, with the JIT off per 9.0(e).

### 9.8 Back end: LIR → A64, with proofs (L)

- No register allocation: every LIR local is a slot in a frame of the
  value-stack region, and each LIR instruction is a fixed template over
  scratch registers. That is slower, but each template's proof is local.
- Per-template refinement of LIR semantics, then composition over
  structured control flow.
- The output always passes 9.5. The proofs show that the back end emits
  only the validator's recognizable sequences, so a validator refusal of
  back-end output is a bug, and a test checks it never happens.

### 9.9 JS front end: bytecode → LIR, with proofs (L)

- One lowering per bytecode op:
  - fast paths inline: small-integer arithmetic with overflow checks, `f64`
    arithmetic, comparisons, branches, property get and set through an
    inline cache's data;
  - everything else is an exit.
- Proof per op: the LIR sequence refines `step`. The fast path refines it
  when its guard holds, and the exit refines it by deferring to the
  interpreter's own handler.
- Tiering: a function is compiled after N entries or loop back-edges, and
  entry from the interpreter at a loop head uses the shared frame (OSR).

### 9.10 Code cache, memory bounds, hostile pages (M)

- Bound the bytes of code per renderer. When it is full, evict and fall back
  to the interpreter.
- Hostile pages: huge functions, deep recursion, pathological inline-cache
  churn. None may crash a renderer or exceed its bounds.

### 9.11 Status, README, VERIFICATION.md (S)

- The TCB lists the A64 semantics' faithfulness, the enter stub and the OS's
  W^X.
- The README states which ops are proven and which platforms run the JIT.

## Risks

- **The ISA spec is wrong for a corner case.** That is the one assumption
  the safety claim rests on. It is mitigated by keeping the subset small,
  the independent transcription and the hardware differential tests, and by
  adding instructions only when the back end needs them.
- **The validator's recognizable sequences constrain the back end.** For
  example, a bounds check must sit in the same basic block as its access.
  That is accepted for a baseline tier. An optimizing tier would need either
  a richer validator (abstract interpretation with proof certificates
  emitted by the compiler) or translation validation.
- **Exit-based runtime calls cost an exit and an entry per slow op.** It is
  measured in 9.2. If it dominates, the fix is a wider fast path, not
  calling Rust from generated code.
- **Phase 7's choices slip.** Without 9.1's constraints (shared frames,
  NaN-boxing, data inline caches), the JIT needs deoptimization metadata
  and stack maps, and a large part of this plan grows.

## Looking ahead

- **WebAssembly.** A new `clazel-wasm` crate holds a Wasm binary decoder and
  validator (our own parser, rule 8), with Wasm → LIR proven against a Verus
  transcription of the Wasm specification (WasmCert-Coq and WasmCert-Isabelle
  as independent sources). It reuses the back end, the validator, the enter
  stub and the sandbox changes unchanged:
  - linear memory is one more region;
  - `memory.grow` and host calls are exits;
  - traps are exits.

  JS↔Wasm calls go through the same frame region, and the JS API's value
  conversions are proven at the boundary.
- **x86-64:** `clazel-x64` and its own validator theorem, behind the same
  LIR.
- **An optimizing tier:** speculation with deoptimization to the shared
  frame layout, and register allocation, each needing translation
  validation or a certificate-checking validator. This is research-grade,
  and is not promised.
