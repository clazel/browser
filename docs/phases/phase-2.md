# Phase 2: Kernel and IPC, detailed plan

**Goal:** the process model every later phase runs inside, in the style of
Quark (Jang, Tatlock and Lerner, "Establishing Browser Security Guarantees
through Formal Shim Verification", USENIX Security 2012). A small kernel
process owns all cookie and storage state (and, from Phase 3, the network).
Each tab is a sandboxed renderer process whose only channel to anything is a
socket to the kernel, carrying typed messages in a format we parse ourselves.
Same-origin policy is not a convention the renderers follow: it is a theorem
about the kernel's step function, which every renderer message passes
through as raw bytes.

Nothing in this phase fetches from the network. Renderers run scripted
operations, not web pages; HTML arrives in Phase 4 and JavaScript in Phase 7.

## Exit criteria

Phase 2 is done when all of these hold on macOS arm64 and Linux x86-64:

1. `clazel-ipc`, `clazel-psl`, `clazel-origin`, `clazel-cookie` and
   `clazel-kernel` are at **tier 2**, accepted by `cargo xtask check`, and
   `clazel-sandbox` is at **tier 1**.
2. `clazel-kernel` proves the theorems in item 2.11, by those names. The
   headline one, `theorem_cookie_noninterference`, says: for renderers
   whose hosts have different cookie roots (defined in 2.4), nothing one
   does changes any byte the kernel sends the other, except through the
   URLs it navigates to, which the kernel treats exactly as if the user had
   typed them (stated precisely in 2.11). In particular neither can read,
   write, evict or detect the other's cookies. Each theorem has at least
   one certified `killed` mutation that breaks it.
3. `cargo run -p clazel -- demo` starts the kernel and two sandboxed renderer
   processes, one committed to `https://a.test/` and one to
   `https://b.test/`, runs scripted `document.cookie` operations in both, and
   prints that neither saw the other's cookies. The adversarial tests in 2.16
   pass: a renderer sending arbitrary bytes, and a renderer trying to reach
   files, sockets or other processes directly.
4. `scripts/verify.sh` exits 0, with the README table showing conformance
   pass rates for the new crates.
5. CLAUDE.md, VERIFICATION.md and the checker match the sandbox and
   `unsafe` decision recorded in 2.0, and `clazel-sys` has a current audit.

## What is proven, and what is assumed

The security claim has three layers. Only the first is proven.

1. **Proven (Verus):** the kernel's step function, from the raw bytes a
   renderer sent to the raw bytes the kernel sends back, including the IPC
   decoder, the cookie algorithms (RFC 6265bis), the Public Suffix List
   lookup, and origins. The isolation theorems are statements about this
   function over all traces.
2. **Small and unproven (Tier 0, listed in the TCB):** the kernel host shell
   that reads frames from sockets and calls the step function. Its one
   security duty is to attach the right renderer id to each frame, which it
   gets from *which socket* the frame arrived on, never from the frame. It
   is kept short enough to read in one sitting, and its line count is in the
   README table.
3. **Assumed (OS, in the TCB already):** that the sandbox leaves the renderer
   no channel except its socket. Seatbelt on macOS; seccomp-BPF, Landlock and
   namespaces on Linux. The Linux filter program is generated by our own code
   and checked exhaustively by Kani (2.14); the OS enforcing it is assumed.

Not covered by any theorem, and said so in the README: timing and other side
channels, resource exhaustion (CPU, kernel memory, message floods), and
transient-execution attacks. Process isolation is the mitigation for the
last; the noninterference theorem is about functional behaviour only.

### 2.0 The sandbox and `unsafe` decision (S)

The options below were put to the maintainer, who asked for the most secure
and verifiable one to be chosen; the decision is at the end of this item.

Renderers must be confined by the OS, or the kernel's theorems are moot: a
renderer that can open the profile directory reads the cookies without
asking. Entering the sandbox needs calls Rust's standard library does not
have: `sandbox_init` on macOS (deprecated, but what Chromium and Firefox
still use); `prctl(PR_SET_NO_NEW_PRIVS)`, `seccomp(SECCOMP_SET_MODE_FILTER)`,
the three `landlock_*` system calls and `unshare` on Linux. Every one is an
FFI call, so `unsafe` somewhere. CLAUDE.md rule 1 allows `unsafe` only in "a
future audited `sys` crate", and rule 8 allows shipped dependencies for "OS
and windowing bindings". Spawning and IPC do *not* need `unsafe`:
`std::os::unix::net::UnixStream::pair()` gives a socket pair, and
`std::process::Command` can hand one end to the child as its stdin through
`Stdio::from(OwnedFd)`. So the question is only how to enter the sandbox.

**Option A: allowlisted OS-binding crates.** Add `libc` and safe wrappers
such as `seccompiler` (Firecracker's), `landlock` and `nix` or `rustix` as
`shipped` rows in DEPENDENCIES.md. Our code stays free of `unsafe` on Linux.
Costs: these crates hold far more `unsafe` than we would use (`rustix` and
`nix` wrap most of POSIX), so "audited" would mean auditing them, at every
version bump; `landlock` brings `enumflags2` and `thiserror`, more rows. No
maintained crate wraps `sandbox_init`, so macOS still needs our own FFI,
which means A does not avoid the question on macOS; it only moves the Linux
half of it.

**Option B: our own audited `clazel-sys` crate.** The one crate that
overrides `unsafe_code` (the workspace `Cargo.toml` already anticipates
this). It declares the handful of functions above and wraps each in a safe
function with a narrow type (`fn apply_seccomp(program: &BpfProgram) ->
Result<(), Errno>`), one `unsafe` block per call with a `// SAFETY:` comment
citing the man page. Its only shipped dependency would be `libc`, for
correct struct layouts and constants per target (getting those wrong by hand
is undefined behaviour). Everything that decides *what* the sandbox allows
lives in safe, verified `clazel-sandbox`. Costs: a checker change (exactly
one named crate may override `unsafe_code`, and only that lint), a change to
CLAUDE.md rule 1 and VERIFICATION.md's Tier 0 row, and Miri cannot check
FFI, so that crate's evidence is the audit and the integration tests.

**Option C: OS-provided launchers, no `unsafe` at all.** Start renderers
with `/usr/bin/sandbox-exec -p <profile>` on macOS and `bwrap` (bubblewrap)
with `--seccomp <fd>` on Linux, both through `std::process::Command`. No
`unsafe` in the workspace, no new shipped dependency. Costs:
`sandbox-exec` is deprecated and undocumented, and Apple may remove it;
`bwrap` is an external program users must install, with its own setuid or
user-namespace requirements; and both are larger TCB components than five
system calls. Passing the filter to `bwrap` on a numbered descriptor is hard
without `pre_exec` (which is `unsafe`), so it would go through stdin, and
the IPC socket through stdout.

**Recommendation: B**, with `libc` as its only shipped dependency, and C
allowed as a stopgap for the demo if Phase 2 should finish before the
`unsafe` exception is opened (not taken; see the decision below). B puts the least foreign `unsafe` in
the TCB, keeps every policy decision in verified code, and is what rule 1
already describes. Whichever is chosen, renderers **fail closed**: if any
sandbox layer cannot be applied (no Landlock in the running kernel,
unprivileged user namespaces disabled as on recent Ubuntu), the renderer
exits before reading input, and the kernel reports why.

A related question: rule 1 says "audited", while
VERIFICATION.md says no step may depend on a human approving something.
Either the sys crate is the stated exception to that (a human audit,
recorded), or "audited" is defined as machine checks: `unsafe` only in that
crate, one FFI call per block, a `// SAFETY:` comment on each, no raw
pointer arithmetic, a fixed list of permitted foreign functions enforced by
`cargo xtask check`, and integration tests that each sandbox layer denies
what it should. (Answered below: both machine checks and an LLM audit.)

**Decision (2026-10-21): option B**, `clazel-sys` with `libc` as its only
shipped dependency, and no option C stopgap. Chosen by the agent at the
maintainer's request, on these grounds:

- *Least foreign `unsafe` in the TCB.* B's `unsafe` is a handful of FFI
  calls we can read in full; A adds tens of thousands of lines of wrapper
  crates, and C adds `bwrap` and `sandbox-exec`, both larger than the calls
  they replace, and the latter deprecated.
- *Every policy decision stays verified.* What the sandbox allows is built in
  `clazel-sandbox` (Tier 1, exhaustive filter check); `clazel-sys` only
  hands the result to the OS and decides nothing.
- *The constraints are machine-checkable,* which a third-party crate's are
  not.

Maintainer's answers to the other questions, same date:

- **"Audited" means machine checks plus an LLM audit.** `cargo xtask check`
  enforces: `unsafe_code` overridden in `clazel-sys` and nowhere else, and
  only that lint; a fixed list of permitted foreign functions; one FFI call
  per `unsafe` block, each with a `// SAFETY:` comment; no raw pointer
  arithmetic; every public function safe. In addition, every change to
  `clazel-sys` gets an audit by a different LLM session from the one that
  wrote it, recorded in `docs/SYS-AUDITS.md` with the SHA-256 of the crate's
  source, and `check` fails if the latest audit's hash does not match the
  source. The checker cannot tell which session wrote an audit; that an
  author never audits its own change is a rule in CLAUDE.md, not a machine
  check, and is stated as such. The audit checks each `unsafe` block
  against the man page and the `libc` declaration it uses.
- **Renderers fail closed** (accepted).
- **Per-root cookie eviction, no global limit** (accepted; see 2.9).
- **The README's memory-safety claim is reworded, not kept by moving
  `unsafe` elsewhere.** "100% safe Rust. `unsafe` is forbidden
  workspace-wide." stops being true when `clazel-sys` lands. Keeping it true
  with option A or C would only move more `unsafe` out of the workspace and
  out of sight; the honest measure is how much `unsafe` we trust, and B keeps
  that smallest. The new wording is along the lines of "100% safe Rust
  except `clazel-sys`: N `unsafe` blocks (M lines) that enter the OS
  sandbox, machine-checked and audited", where N and M are not typed:
  `cargo xtask report` counts `unsafe` blocks and their lines per crate in
  the generated table (as it counts axioms), and `verify` fails if the
  README sentence's numbers differ from that count.

**Done when:** CLAUDE.md rule 1, VERIFICATION.md (Tier 0 row, TCB list)
and the checker say exactly the above; the README claim is reworded in the
same commit that adds `clazel-sys`'s first `unsafe` block, never before or
after, with the `unsafe` count in the generated table; `docs/SYS-AUDITS.md`
exists; and
planted violations are caught: a second crate overriding `unsafe_code`, an
unlisted foreign function, an `unsafe` block without `// SAFETY:`, a
`clazel-sys` source change with a stale audit hash, and a README `unsafe`
count that differs from the measured one.

**As built:** `crates/clazel-ipc/src/cbor/{spec,contract,termination}.rs`
(commit `6b27b5c`, one small fix after it). The spec represents an item by
its **pre-order token sequence** (`Token::Array(n)` followed by its
elements' tokens), which is a bijection with the RFC's tree and makes every
function a loop over tokens, so termination follows from the position
advancing; this and the other modelling choices are listed at the top of
`spec.rs`. `decode_from` carries an owed-item count instead of recursing
into arrays, and rejects trailing bytes (a frame holds exactly one item). A
string's length must be below 2^64 (`token_ok`). `lemmas.rs` already proves
the three lemmas that 2.2 lists, because they are facts about the spec:
`lemma_decode_encode`, `lemma_encode_decode` (so `lemma_decode_injective`)
and `lemma_decode_alloc_bound`. `examples.rs` evaluates 26 Appendix A items
and 30 rejections (every non-shortest width, each major type outside the
profile, indefinite lengths, truncation, trailing bytes, bad UTF-8).
`mutations.json` has 49 CBOR mutations, each `killed` with a certificate.
Text validity is `clazel-encoding`'s `decode_without_bom_or_fail`. There is
no recursion depth limit because the decoder never recurses.

**As built:** CLAUDE.md rule 1, VERIFICATION.md (Tier 0 row, TCB list, a new
"The `unsafe` exception" section) and `docs/SYS-AUDITS.md` (format, hash
definition, auditor instructions, no rows) say what the decision says.
`cargo xtask check` (`xtask/src/sys.rs`) enforces: `unsafe_code` overridden
only by `crates/clazel-sys`'s manifest, which must list the workspace lints
itself (a crate cannot both inherit them and override one) with every other
lint equal to the workspace's; `libc` as its only dependency, pinned
exactly, and no `build.rs`; every `unsafe` a block or `unsafe extern` block;
one call per block, to `sandbox_init`, `sandbox_free_error`, `prctl`,
`unshare` or `syscall` (only with the numbers of `seccomp` and the three
`landlock_*` calls); no dereference inside a block; a `// SAFETY:` comment
directly above each, citing `man <section> <name>`; no pointer arithmetic
methods, `macro_rules`, `include` or `#[path]` in the crate; no `pub`
foreign declaration and no `pub use` of `libc`; the audit hash; and the
README sentence's counts. The report table has an `unsafe` blocks (lines)
column, and the README sentence is `check`ed, so `verify` fails on a wrong
count. Each planted violation is a unit test in `sys.rs`.

`clazel-sys` has 8 `unsafe` blocks (11 lines). On Linux: `set_no_new_privs`,
`seccomp_set_mode_filter(&[SockFilter])`, `landlock_deny_filesystem(u64)` and
`unshare(Namespaces)`. On macOS: `sandbox_init_profile(&str)`. Departures from
the sketch above: `landlock_add_rule` is permitted by the checker but not

### 2.1 IPC wire format: spec and contracts (M)

The IPC codec parses bytes from an untrusted renderer, so it is ours (rule
8) and Tier 2 (VERIFICATION.md). Rather than invent a format, use a strict
profile of CBOR (RFC 8949), so the wire format has a standard, official test
vectors and independent implementations to diff against, which a bespoke
format would not:

- major types 0 (unsigned integer), 2 (byte string), 3 (text string),
  4 (array), and the simple values false and true (major type 7, 20 and 21);
- nothing else: no negative integers, maps, tags, floats, null, undefined or
  indefinite lengths;
- RFC 8949 §4.2.1 core deterministic encoding: arguments in preferred
  (shortest) form. A decoder **rejects** every non-shortest form, so each
  value has exactly one encoding;
- text strings must be valid UTF-8 (§3.1 major type 3), checked with
  `clazel-encoding`'s fatal decoder.

`spec.rs` transcribes RFC 8949 §3 (the initial byte, argument and the five
major types used) and §4.2.1 for the profile, and lists the profile's
restrictions as modelling choices. Contracts: `decode(&[u8]) ->
Option<Item>` and `encode(&Item) -> Vec<u8>`.

**As built:** the profile's spec is `crates/clazel-ipc/src/cbor/spec.rs` and
its contracts `cbor/contract.rs`; the implementation, independent
transcription and conformance are under 2.2.

### 2.2 IPC wire format: implementation, independent transcription, conformance (M)

Implementation proven against 2.1's contracts. Lemmas:
`lemma_decode_encode` (decode inverts encode), `lemma_encode_decode`
(encode inverts decode wherever decode succeeds, so the profile is
canonical: no two byte strings decode to the same item, which rules out
parser differentials between kernel and renderer), and
`lemma_decode_alloc_bound` (the decoder never reserves more elements than
there are bytes left, so a declared array length of 2^64 cannot exhaust
memory).

Independent: RFC 7049 (the original CBOR, 2013) §2 and its Appendix C
decoder pseudocode, plus §3.9 "Canonical CBOR", written without reading
`spec.rs`, proven equal on the profile. A different revision is not a
different body, so the conformance tests carry more weight here.

Conformance: RFC 8949 Appendix A examples from the `cbor/test-vectors`
repository (`appendix_a.json`), vendored with `SOURCE.md` and converted by
`cargo xtask testdata`. Vectors inside the profile must decode to the stated
value and re-encode to the same bytes; every vector outside it must be
rejected, and the test counts both. Differential against `ciborium` or
`minicbor` (new `test` rows in DEPENDENCIES.md; pick whichever has fewer
dependencies) on random items and random byte strings: where the other
accepts a non-shortest form, we must reject it, and that is the only
permitted difference.

**As built:** `cbor/{decode,encode,token}.rs`: `decode(&[u8]) ->
Option<Vec<Tok>>` and `encode(&[Tok]) -> Vec<u8>`, where `Tok` is the exec
twin of the spec token and an item is a `Vec<Tok>`. Both are proven equal
to the spec (`contract.rs`). The decoder is a loop; it returns `None` as
soon as the owed count exceeds the bytes left, so a declared length of 2^64
allocates nothing, and pushes only tokens it has read
(`decode_alloc_ensures`). `independent.rs` is a second transcription from
RFC 7049 §2, Appendix C and §3.9 (bit operations, widths `2^(ai-24)`,
shortest form as a `class_of` function, recursion on the rest of the input),
with text validity from `clazel-encoding`'s Unicode Table 3-7
transcription; `lemma_equals_decode` proves it equal to the spec on every
input and `lemma_ind_is_item` proves the item predicates equal. It was
written by the same agent that wrote `spec.rs`, so it is weaker evidence
than a second author's. Conformance (`tests/conformance_cbor.rs`): 82/82
vectors of `cbor/test-vectors` `appendix_a.json` (26 inside the profile
decode and re-encode, 56 are rejected; the file is RFC 7049's Appendix A,
which RFC 8949 repeats), and a differential against `minicbor` 2.3.1
(20 000 random items, 60 000 random and mutated byte strings; where we
reject, minicbor must accept only non-shortest bytes). No difference was
found. `minicbor` was chosen over `ciborium` (fewer dependencies: none).
The upstream repository has no licence file; `LICENSE.md` says so.

### 2.3 IPC frames and message schema (M)

A frame is a 4-byte big-endian length (at most `MAX_FRAME`, 1 MiB to start)
followed by exactly one CBOR item filling the rest of the frame. A message
is an array whose first element is a tag. Renderer to kernel:
`CookieGet`, `CookieSet { cookie_string }`, `StorageGetItem`,
`StorageSetItem`, `StorageRemoveItem`, `StorageClear`, `StorageKey`,
`StorageLength`, `Navigate { url }`. Kernel to renderer: `Commit { url,
script }`, `CookieValue`, `StorageValue`, `Error`. Two rules are part of the
schema's spec and checked by mutations:

- **No message carries a claimed identity.** No origin, renderer id, tab id
  or URL of the sender appears in any renderer-to-kernel message. The kernel
  learns the sender from the socket (layer 2 above).
- **Renderer ids never reach a renderer.** They are assigned in order, so
  showing them would let one renderer count another's spawns.

Typed `decode_message(&[u8]) -> Option<Message>` and `encode_message`,
proven against the schema spec, with the same three lemmas as 2.2 lifted to
messages and frames. The schema is ours, so it has no second transcription;
`clazel-ipc`'s `independent.rs` is the CBOR one from 2.2, and the schema's
evidence is its round-trip and canonicity lemmas and the end-to-end tests
in 2.16.

**As built:** `frame/` and `message/` (spec, contract, lemmas, examples,
codec each). `MAX_FRAME` is 1 MiB; `payload_length` lets the transport
refuse an oversized frame from its first 4 bytes. `decode_frame`,
`encode_frame`, `decode_message`, `decode_renderer_message` (only
renderer-to-kernel tags), `decode_framed`, `encode_message` and
`encode_framed` are proven equal to the spec. The schema adds
`StorageLengthValue` (tag 104) to the plan's list, because `StorageLength`
needs a reply; `StorageValue` carries a presence flag, because the profile
has no null. Proven: `lemma_decode_encode_message`,
`lemma_encode_decode_message` (so `lemma_decode_message_injective`),
`lemma_decode_message_alloc_bound`, the same two for frames, and the two
schema rules as `lemma_no_identity_fields` over a `message_fields` table
that has identity variants (`Origin`, `RendererId`, `TabId`, `SenderUrl`)
no message uses, tied to the wire by `lemma_fields_match_tokens`. That table
is a view of the schema, not the encoder itself: the rules hold because
`Message` has no such field, and the mutations show the lemmas fail if the
table is changed. 69 mutations in all, every one `killed` with a
certificate. One mutation was dropped because it is equivalent: the
array-length check in `parse_message` is redundant for valid items.
`tests/messages.rs` round-trips every variant through the real code.
`clazel-ipc` is at tier 2 for all of it (177 Verus obligations).


### 2.4 Public Suffix List (L)

Needed by "same site" (2.5) and by the cookie storage model (2.9, which
refuses a Domain attribute that is a public suffix). URL §3.2 "public
suffix" and "registrable domain", which call "obtain a public suffix" over
the Public Suffix List. Vendor the list (`public_suffix_list.dat`) from
`publicsuffix/list` at a pinned commit, ICANN and private sections both
(browsers use both), with its SHA-256 in `SOURCE.md`; `cargo xtask tables`
generates the rule tables, as for UTS #46 in 1.8, reusing its chunked opaque
tables and bisection lookup. The proof is relative to the tables; `check`
fails if the generated file differs.

Also defined here, because 2.9 and 2.11 need it and the standards do not
name it: the **cookie root** of a domain, the shortest suffix of it (in
labels) that is not a public suffix, or the domain itself when every suffix
is a public suffix; for an IP address, the address. See 2.9 for why this,
and not the registrable domain, is the cookie isolation boundary.

Independent: the "Formal algorithm" on publicsuffix.org (written by Mozilla,
not WHATWG), transcribed without reading `spec.rs` and proven equal.
Conformance: the list's own `tests/tests.txt` (`checkPublicSuffix` cases),
vendored from the same commit. Differential against the `publicsuffix`
crate loaded with the same vendored list (a `test` row), on every rule's
domain plus random labels above it.

**As built (partial, `clazel-psl` stays at tier 0):** `data/publicsuffix-5dd321ff/`
vendors `public_suffix_list.dat`, `tests.txt` and the licence from
`publicsuffix/list` at `5dd321ff` with SHA-256 in `SOURCE.md`; `cargo xtask
tables` (`xtask/src/psl.rs`) generates `src/data.rs` (10396 rules, 24423
labels, chunked opaque tables; Unicode labels become A-labels with an RFC 3492
encoder in xtask), and `check` fails if it is stale. `spec.rs` transcribes the
formal algorithm and URL §3.2 over any `Seq<Rule>`, with the cookie root as 2.4
defines it; modelling choices (empty labels give null, one-pass prevailing
rule, trailing dot) are at its top. `exec.rs` is proven equal to the spec on
the generated list (73 Verus obligations, 0 errors). It scans every rule
instead of bisecting, because Verus cannot see that the opaque tables are
sorted and the spec is "match against all rules"; a rule that cannot beat the
best so far is skipped before matching. Evidence: `tests.txt` 78/78 (inputs
canonicalized by the proven host parser) and a differential against
`publicsuffix` 2.3.0 on every ASCII rule plus labels above it, 49685/49685.
`examples.rs` evaluates the spec on concrete domains and a five-rule list
(`com`, `uk`, `co.uk`, `*.ck`, `!www.ck`): plain, longest, wildcard,
exception and default rules, the trailing dot, empty labels, the registrable
domain and the cookie root of registrable domains, public suffixes, wildcard

### 2.9 Cookie storage and retrieval (L)

RFC 6265bis §5.7 storage model and §5.8 retrieval model, with the jar as a
sequence of cookie records and the current time as an input. The request
URL is an abstract record (scheme, canonical host, path), so the algorithms
need no URL parser; only the conformance rows that start from a URL string
use 1.10's. §5.2 "same-site" and "cross-site" requests are transcribed over an
abstract request context, using 2.5's "same site"; in Phase 2 the only
caller is `document.cookie`, a non-HTTP API in a top-level document, and the
real request contexts arrive with Fetch in Phase 3.

**Two places where a literal reading would break isolation**, both decided
here and listed as modelling choices:

- **The isolation boundary is the cookie root, not the registrable domain.**
  A cookie set by `amazonaws.com` with `Domain=amazonaws.com` is sent to
  `bucket.s3.amazonaws.com`, whose registrable domain is
  `bucket.s3.amazonaws.com` (`s3.amazonaws.com` is a public suffix). So a
  theorem partitioning the jar by registrable domain would be false. Two
  hosts can share a cookie exactly when they have the same cookie root
  (2.4). `lemma_store_within_root`: every cookie stored for a request to
  host h has a domain whose cookie root is h's. `lemma_retrieve_within_root`:
  retrieval for host h returns only cookies whose domain has h's cookie
  root. `lemma_store_frame`: storing for host h leaves every cookie of
  another root unchanged.
- **Eviction is per cookie root, never global.** §5.7's last step lets the
  user agent evict when the store is too large, and §6.1 suggests a global
  total (3000 cookies). A global limit lets one site evict another's
  cookies by setting many of its own, which is both a write and, by
  probing, a read across sites. We keep only a per-root limit (180, as
  Chrome and Firefox use per domain; the RFC asks for at least 50) and no
  global one. The RFC
  leaves the eviction policy to the user agent, so this is a choice, not an
  erratum. Memory stays bounded because a renderer can only add cookies
  under its own root.

Phase 2 versus Phase 3, by section:

| RFC 6265bis | Phase 2 | Phase 3 |
|-------------|---------|---------|
| §5.1 dates, hosts, domain and path matching | all | — |
| §5.2 same-site requests | the algorithm, over abstract contexts | wired to Fetch request contexts, redirects |
| §5.3 ignoring Set-Cookie | the non-HTTP-API cases | HTTP responses |
| §5.4 name prefixes, §5.5 lifetime limit | all | — |
| §5.6 Set-Cookie parsing | all (document.cookie uses it) | HTTP `Set-Cookie` headers from the HTTP parser |
| §5.7 storage model | all, non-HTTP API flag set by the kernel | HTTP API path, `Secure` from real TLS |
| §5.8 retrieval model | all, for document.cookie | the `Cookie` request header (Fetch) |
| persistence to disk | no (the jar lives in kernel memory) | a format of our own, Tier 2 |

Not in either: partitioned cookies (CHIPS) and third-party cookie blocking,
which are not in 6265bis.

### 2.10 Kernel state machine: spec and contracts (L)

The kernel is a pure function `step(State, Event) -> (State, Seq<Output>)`:

- **State:** renderers (id, tab, committed URL, origin lock), the cookie jar
  (2.9), Web Storage (a map from origin to a list of key and value pairs,
  HTML §12.2.1; only for tuple origins), the next fresh id, the current time.
- **Events:** `FromRenderer(id, bytes)` (raw frame bytes, so decoding is
  inside the proven function and the theorems cover malformed input),
  `OpenTab(url)` and `NavigateTab(tab, url)` from the user (a URL typed
  into a new or an existing tab; `url` is absolute), `RendererExited(id)`
  and `Tick(time)`. A renderer's `Navigate { url }` is handled as the
  kernel resolving `url` against that renderer's committed URL and then
  doing exactly what `NavigateTab(its tab, resolved)` does; 2.11 relies on
  this.
- **Outputs:** `ToRenderer(id, bytes)`, `Spawn(id, policy)`, `Kill(id)`.

Each renderer is **locked to one origin**, the origin of the URL it
committed, chosen by the kernel. A navigation to a different origin always
gets a new renderer process and kills the old one (a stricter rule than
Chromium's per-site locks; one renderer, one origin). Requests from a
renderer are answered for its lock and committed URL, never for anything in
the message. The document.cookie getter and setter follow HTML's steps
(return the empty string, or ignore, for an opaque origin; otherwise call
6265bis retrieval or storage with the non-HTTP API flag); localStorage
follows HTML §12.2, keyed by the origin. Storage events to other documents
are not modelled (no renderer receives anything it did not ask for); this
is listed.

The URL-to-origin function is a **parameter** of the spec (`spec_fn(Seq<u32>)
-> Option<Origin>`), and every contract and theorem quantifies over it, so
the kernel proofs do not unfold the URL parser's. 2.13 instantiates it with
the real parser.

**As built (spec and contracts done; the implementation is 2.12, which took
`clazel-kernel` to `tier = 2`; 2.12 added scalar-valued URLs to `step_requires`):** `crates/clazel-kernel/src/`.
`spec.rs` has the state (`State`: `renderers: Seq<Renderer>` with id, tab,
committed URL as code points and lock; `jar: Seq<Cookie>`; `storage:
Map<Origin, Seq<StorageEntry>>`; `next_id`; `now`), `Event` (`FromRenderer
{ id, bytes }`, `OpenTab { url, script }`, `NavigateTab { tab, url, script }`,
`RendererExited { id }`, `Tick { time }`), `Output` (`ToRenderer`, `Spawn`

modelling choices at the top. `invariant.rs` has `kernel_wf` and its proofs,
`domain.rs` the definitions of 2.11 below, and `contract.rs` the contract of

`step` over the generated Public Suffix List, for any `UrlFns`) and of its

items:**

- **Three URL functions, not one** (`UrlFns`): `origin_of` is the plan's
  `spec_fn(Seq<u32>) -> Option<Origin>`; `path_of` (the path serialization,
  which cookie matching needs and an origin does not hold) and `resolve`
  (basic URL parser with a base, then serializer) are also needed, the second
  for a renderer's `Navigate`. 2.13 instantiates all three, and must give a
  URL whose origin is a tuple only if its host canonicalizes to a non-empty
  name (always so for parsed `http`, `https`, `ws`, `wss`, `ftp`), because
  the kernel refuses other URLs (`valid_tuple_origin`). An opaque origin from
  `origin_of` is ignored: the lock is `Opaque(renderer id)`, so an
  opaque-origin renderer is a domain of its own.
- **Where the script comes from:** `OpenTab` and `NavigateTab` carry it (the
  user's actions; the demo, 2.16, types it in). A renderer's own `Navigate`
  commits `no_script()` (empty), so the renderer it creates gets the resolved
  URL and nothing else from the navigating renderer. 2.11's declassified
  event is `NavigateTab(tab, resolved, no_script())`, and
  `lemma_declassified_is_navigate_tab` proves `step` of the `Navigate` equals
  `step` of it. 2.15's renderer stub therefore only runs scripts it gets from
  user-initiated tabs.
- **`theorem_reply_only_to_sender` needs one exception.** A `Navigate` to a
  different origin spawns a renderer and sends it the `Commit` in the same
  step, so a `FromRenderer(r, _)` event's `ToRenderer` outputs are for `r` or
  for the renderer spawned in that step (id `next_id` of the state before).
  Same-tuple-origin navigation keeps the renderer and re-commits to it; an
  opaque-origin target always spawns.
- **A document on a public-suffix host is cookie-averse (added by 2.11).**
  `cookie_averse(rules, lock)` is also true when the lock's host is a public
  suffix (`co.uk`, `github.io`), as in Chrome and Firefox. It closes the one
  flow of RFC 6265bis that crosses cookie roots (§5.7 step 16's whole-jar scan
  with a host-only public-suffix cookie), `kernel_wf` gained
  `jar_no_public_suffix`, and the contract of 2.12 is unchanged in shape.
  Item 2.13's real URL parser changes nothing here; a URL on such a host is
  still committed (so a renderer exists), it just gets no cookies.
- **Malformed input:** an id naming no renderer is ignored (no state change,
  no output); a frame that does not decode, or decodes to a message a renderer
  may not send, gets `Kill(id)` and the record removed (the tab closes); a
  request that cannot be served gets an `Error` reply (`error_security`
  for `localStorage` of an opaque origin, `error_quota`, `error_bad_url`,
  `error_encode` for a reply that is not one frame). Frames are whole frames
  (`decode_framed`), so the host shell (2.15) passes the 4-byte header too and
  turns a frame over `MAX_FRAME` or a closed socket into `RendererExited`.
- **`document.cookie` and opaque origins.** HTML's getter and setter return
  empty / do nothing for a cookie-averse document (URL scheme not `http` or
  `https`) and throw a "SecurityError" for an opaque origin. Every URL with an
  opaque origin has such a scheme, so the SecurityError branch is unreachable
  and an opaque lock gets the empty string, as this plan said; the argument is
  in `spec.rs`. A tuple origin of `ws`, `wss` or `ftp` is cookie-averse too.
  `localStorage` of an opaque origin does get an `Error` (HTML throws).
- **Web Storage** is an ordered list per tuple origin with a per-origin quota
  of 5 MiB of keys and values (HTML's "QuotaExceededError"), no storage events.
  Time is monotone: `Tick(time)` sets `max(time, now)` and evicts expired
  cookies.
- **Tabs:** a tab id is the id of its first renderer and survives navigation
  to another origin; a renderer exiting closes its tab.

**`kernel_wf` is proven preserved**, not just recorded: `lemma_init_wf`,
`lemma_step_preserves_wf` (from 2.9's `lemma_store_bounds`,
`lemma_store_preserves_domains_nonempty` and `lemma_evict_expired_props`, plus
lemmas here for retrieval and for the renderer table and storage) and
`lemma_reachable_wf`. It says: `jar_domains_nonempty`, `jar_within_root_limit`,
`jar_keys_unique`; ids and tabs distinct and below `next_id`, and each
renderer's lock equal to `lock_of_url` of its committed URL; storage maps only
for valid tuple origins, non-empty, with unique keys and within the quota.
**For 2.11** `domain.rs` defines `Domain` (a cookie root, or `Opaque(id)`),
`domain_of_renderer`, `obs`, `event_domain`, `declassified`, `ipurge_event`,
`ipurge` and `purge`; the theorems and unwinding lemmas are 2.11's. No
mutations yet (they come with the theorems).

### 2.11 Isolation theorems (L)

Stated over 2.10's spec, for every URL-to-origin function, every reachable
state and every trace:

- `theorem_reply_only_to_sender`: a `FromRenderer(r, bytes)` event produces
  `ToRenderer` outputs only for r.
- `theorem_lock_is_committed_origin`: in every reachable state, each
  renderer's lock is the origin of its committed URL, and only `OpenTab` and
  `Navigate` handling, which the kernel parses itself, set it.
- `theorem_cookie_confidentiality`: the `CookieValue` the kernel sends r is
  exactly HTML's document.cookie getter for r's committed URL over the jar
  at that moment: 6265bis retrieval with the non-HTTP API flag, so no
  HttpOnly cookie and nothing that URL's host and path would not get.
- `theorem_cookie_integrity`: after `FromRenderer(r, bytes)`, the jar is
  either unchanged or 6265bis storage applied to the decoded cookie string
  with r's committed URL and the non-HTTP API flag; after any other event
  it is unchanged except for expiry at `Tick`.
- `theorem_storage_same_origin`: storage replies to r read only the map for
  r's lock, and storage requests from r write only that map.
- `theorem_cookie_noninterference`: the exit criterion. The observer is a
  **domain** D: a cookie root, or one opaque-origin renderer on its own.
  Each `FromRenderer(r, _)` event belongs to the domain of r's lock at that
  point in the trace. For a trace t, `purge(t, D)` replaces every
  `FromRenderer` event of a domain other than D by its **declassified
  part**: `NavigateTab(tab, resolved url)` if its bytes decode to a
  `Navigate` (2.10), and nothing otherwise. The theorem: for every D and
  every trace t, the outputs addressed to renderers whose domain is D,
  including their `Spawn` and `Kill`, are the same from running t and from
  running `purge(t, D)`, up to a bijection on renderer ids.

  Why the declassified part is needed: a literal "delete every event of B"
  is false. If B, on `b.test`, navigates its tab to `https://a.test/?x`,
  the kernel spawns a new renderer locked to `a.test`, which then reads and
  writes a.test's cookies; delete B's events and that renderer never
  exists. That flow is the web's own (any page may navigate to any URL, and
  the URL may carry data), and it is exactly the flow a user typing the same
  URL would cause, so the theorem names it and allows nothing else: no
  cookie, storage entry, renderer state or timing of B reaches D except
  through the URL B chose. Ids are compared up to a bijection because
  B's navigations take ids from the shared counter; the schema already
  keeps ids out of every message (2.3), so no renderer can see the shift.

  What this means for the exit claim: a renderer on `b.test` cannot read
  a.test's cookies, because nothing flows from a.test's domain to b.test's
  except URLs that renderers locked to a.test navigate to. A page can leak
  its own cookies by navigating to a URL containing them, as on the web
  today; the theorem says that is the only way, and the demo and README
  say so.

  Proven Rushby-style, in the intransitive form ("Noninterference,
  Transitivity, and Channel-Control Security Policies", 1992, §5, with
  `ipurge`): an observation `obs(s, D)` (the records of D's renderers, the
  cookies under D's root, the storage maps for D's origins, the time), and
  four unwinding lemmas, `lemma_output_consistency`,
  `lemma_step_consistency`, `lemma_local_respect` (an event of another
  domain that is not a `Navigate` leaves `obs(s, D)` unchanged) and
  `lemma_navigate_declassify` (a `Navigate` of another domain changes
  `obs(s, D)` exactly as its declassified `NavigateTab` does), from which
  the trace theorem follows by induction. It needs 2.9's within-root and
  frame lemmas and per-root eviction; it is false with a global cookie
  limit, and a mutation shows that.

The cookie-root condition is the real boundary, not a convenience: two
renderers on `a.example.com` and `b.example.com` share the root
`example.com`, and the RFC lets one set a `Domain=example.com` cookie the
other reads. The theorems do not claim otherwise; they claim the kernel
allows no flow beyond the ones 6265bis allows.

Mutations to seed, each needing a certificate against one of these:
answer from a URL inside the message instead of the lock; reply to the
wrong renderer; skip the HttpOnly check for the non-HTTP API; drop the
public-suffix check in storage; evict globally; let a renderer's
`Navigate` keep its old lock; show a renderer id in a reply; let the
renderer spawned by a `Navigate` inherit anything from the navigating
renderer besides the resolved URL (its storage map, say).

The theorem names go in `clazel-kernel`'s `Cargo.toml` metadata
(`theorems = [...]`), and a small `cargo xtask check` extension fails if a
listed theorem is missing from the source, so a theorem cannot be quietly
deleted to get a proof through.

Independent: HTML's document.cookie getter and setter and the Web Storage
algorithms used, transcribed again without reading `spec.rs` and proven
equal; and Quark's definitions of tab non-interference and cookie
confidentiality and integrity (2012 paper, §4), restated for this state
model and proven to follow from the theorems above.

**As built (theorems proven; `clazel-kernel` stayed at `tier = 0` until the
executable kernel, 2.12, took it to tier 2):** `crates/clazel-kernel/src/`. `statements.rs` and
`noninterference.rs` hold the statements as predicates (committed before the

proofs; `projection.rs`, `retrieval_projection.rs` and `store_projection.rs`

name).

- `theorem_reply_only_to_sender`: `ToRenderer` outputs of `FromRenderer(id, _)`
  are for `id` or for the renderer spawned in that step (`next_id`, with its
  `Spawn`); a `Spawn` is for `next_id`; a `Kill` is for `id`.
- `theorem_lock_is_committed_origin`: every renderer's lock is `lock_of_url` of
  its URL (a tuple origin itself, `Opaque(id)` for an opaque one); a lock never
  changes while its id lives; only `OpenTab`, `NavigateTab` and a decoded
  `Navigate` create renderers.
- `theorem_cookie_confidentiality`: the reply to `CookieGet` is exactly
  `html_cookie_getter` (empty for a cookie-averse lock, else 6265bis retrieval
  for the lock's scheme and host and the committed URL's path, non-HTTP), and
  every cookie in it is live, retrieved by `cookie_is_retrieved` for the lock's
  host and not HttpOnly.
- `theorem_cookie_integrity`: see the first correction below.
- `theorem_storage_same_origin`: a storage call changes only the map of its
  lock and nothing else of the state, and its outputs and new map are a
  function of the old map of that lock (and the sender's id) alone.
- `theorem_cookie_noninterference` (and `_from`, from any reachable state, and
  `_up_to_ids`): for every domain `d` and trace `t` with the one hypothesis
  below (`user_tabs_open`), `run_outputs_for(d, t) == run_outputs_for(d,
  purge(t, d))`, the outputs addressed to renderers of `d` (an output is
  addressed to `d` if a renderer of `s` or `s'` with that id is in `d`).
  Proven from `lemma_output_consistency` (a kept event gives the same outputs
  to `d` in both runs), `lemma_step_consistency` (and leaves the states
  related), `lemma_local_respect` (an event of another domain with no
  declassified part leaves the state related to the untouched other run and
  sends nothing to `d`; this covers a `Navigate` that fails to decode or
  resolve) and `lemma_navigate_declassify` (a `Navigate` of another domain
  changes the state and the outputs to `d` as its `NavigateTab` does in the
  other run), by induction over the trace. The relation `rel` is: both states
  well formed, every renderer of the first in the second (the second may keep
  renderers the first lost), the same renderers of `d`, counter and time, the
  same unexpired cookies under `d`'s root and storage maps of `d`'s origins.
  (`kernel_wf` of both, which now includes `jar_no_public_suffix`, supplies
  the rest.) The bijection on ids is the
  identity (the declassified `NavigateTab` takes the same id as the
  `Navigate`); `_up_to_ids` states the plan's form. `obs` changed from 2.10's:
  renderers are a set and cookies the unexpired ones (the proof found both
  necessary).

**Corrections to this plan's text** (each with a counterexample proven in
`counterexamples.rs`; none admits a flow beyond RFC 6265bis's and the
declassified navigation URL):

1. *Integrity.* "unchanged or 6265bis storage" omits §5.8.3 step 5: a
   `CookieGet` updates the last-access-time of the cookies it returns
   (`example_retrieval_changes_jar`), and every cookie call evicts expired
   cookies. The theorem adds those two alternatives. (Not proven: that no
   storage can mimic a retrieval's update; the first alternative of the plan's
   text is shown false, not the second.)
2. *Noninterference needs `user_tabs_open`.* A renderer that sends a frame the
   kernel cannot decode is killed and its tab closed; the purge drops that
   frame, so in the purged run the tab is still open and a user's later
   `NavigateTab` of it spawns a renderer in the observer's domain
   (`example_dead_tab_breaks_noninterference`). The theorem is for traces in
   which the user only navigates open tabs, as a user can. No flow is added:
   in the first run that event is a no-op.
3. *A document on a public-suffix host is cookie-averse in the kernel.* RFC
   6265bis §5.7 step 16 ("Leave Secure Cookies Alone") asks, over the whole
   jar, for a secure cookie whose domain domain-matches the new cookie's domain
   or conversely. A host-only cookie of a public suffix (allowed by step 9, e.g.
   host `co.uk` or `github.io`) matches cookies of `a.co.uk`'s root, so a
   renderer on `x.a.co.uk` could be stopped from storing a cookie by one on
   `co.uk` (`example_public_suffix_overlay_crosses_roots`): the one flow of
   6265bis that crosses a root. This first appeared here as a hypothesis on
   traces (`ps_free_run`); it is now closed in the kernel, by the maintainer's
   decision: `cookie_averse(rules, lock)` is also true when the lock's host is
   itself a public suffix (`lock_on_public_suffix`, over the same `rules`; an IP
   address is not one), so the getter returns the empty string and the setter
   does nothing, as in Chrome and Firefox (HTML has no such condition; listed
   as a modelling choice at the top of `spec.rs`). Then no cookie with a
   public-suffix domain can enter the jar (host-only cookies on such hosts are
   never created, and step 9 already rejects a `Domain` attribute that is a
   public suffix), which is `jar_no_public_suffix`, now a clause of
   `kernel_wf` and proven preserved by `step`. The counterexample remains as
   the record of why and is unreachable in the kernel. The theorem has no
   public-suffix hypothesis. Note `localhost` is not on the PSL, so it is not
   cookie-averse by this rule; a one-label host such as `test` is a public
   suffix only by the default rule `*`, so `a.test` and `b.test` of the exit
   demo are not.

**Independent transcription** (`independent.rs`, written by a separate agent
from the HTML Standard without reading `spec.rs`; text read 23 October 2026):
`document.cookie`'s getter and setter and the Web Storage methods. Proven
equal to the kernel's (`independent_equivalence.rs`) on a stated class: the
document is top-level with the URL the kernel builds (the lock's scheme and
host, the committed URL's path) and the lock's scheme is ASCII; the storage
side for any state, with the kernel's quota as the limit. **Quark**
(`quark.rs`; Figure 7 and §5, "Security Properties", read from the USENIX PDF
of 23 October 2026; the plan's "§4" is §5 there): `tab_NI` in its two-trace
form, between domains (the paper names domains as future work; two tabs of one
root legitimately share cookies), and cookie integrity (`no_xdom_cookie_set`)
and confidentiality, each proven from the theorems.

**Mutations** (`mutations.json`, 9, all `killed` with certificates): wrong
renderer in a reply, renderer id in a reply, request scheme from the URL's
origin instead of the lock (the cookie messages carry no URL, so this is the
nearest to "a URL inside the message"), cookie calls as HTTP requests (skips
the HttpOnly check), cookie-averse test ignoring the scheme, `Navigate` keeping
the old lock, the spawned renderer's `Commit` carrying the navigating
renderer's URL, and a storage key compared to values. The plan's "drop the
public-suffix check in storage", "evict globally" and "skip the HttpOnly check
for the non-HTTP API" are mutations of `clazel-cookie`'s spec and are
`store-step9-public-suffix-check-dropped`, `eviction-victim-ignores-root` and
`retrieval-http-only-skipped` in its `mutations.json` (2.9), killed against
the lemmas the kernel proofs use. The ninth mutation,
`public-suffix-host-not-cookie-averse`, drops the new cookie-averse condition
(certificate: `ml_public_suffix_is_cookie_averse`, over `cookie_averse_given`,
which `cookie_averse` is defined through so that the condition can be
evaluated without the host parser). Not covered by a certificate: storage keyed

### 2.12 Kernel implementation (M)

Exec `step` proven against 2.10's contract, using the exec codecs (2.3),
cookie algorithms (2.9) and origins (2.5). Still pure: no I/O, no clock, no
processes; time and bytes come in as arguments.

Conformance: the converted WPT `cookies/` document.cookie cases (2.9) and a
convertible subset of WPT `webstorage/`, run through the exec kernel as
frames from fake renderers, so through the codec as well. Differential
against `cookie_store` on random multi-renderer traces, comparing each
renderer's document.cookie results.

**As built (`clazel-kernel` is at `tier = 2`):** `crates/clazel-kernel/src/exec/`,
with the contract in `src/contract.rs`.

- **The exec state** (`exec::records`): `StateRecord { renderers:
  Vec<RendererRecord { id: u64, tab: u64, url: Vec<u32>, lock: ParsedOrigin }>,
  jar: Vec<CookieRecord>, storage: Vec<StorageBucket { origin: ParsedOrigin,
  entries: Vec<StorageEntryRecord { key, value }> }>, next_id: u64, now: u64 }`,
  with a `view` to 2.10's `State`: `renderers` and `jar` map their records'
  views, `next_id` and `now` widen, and `storage` is `Map::new(origins of the
  buckets, entries of the bucket of each)` (`storage_view`). Because a `Map`
  has one entry per origin and a vector can repeat one, the exec state has one
  invariant of its own, `exec_wf`: the buckets' origins are distinct and each
  bucket is non-empty. `init_record` has it and `step_exec` keeps it. Events and
  outputs are `EventRecord` and `OutputRecord` with views to `Event` and
  `Output`. `step_exec<U: UrlFnsExec>(urls: &U, s: StateRecord, e: &EventRecord)
  -> (StateRecord, Vec<OutputRecord>)` requires `step_requires(urls.urls(),
  s@, e@)` and `s.exec_wf()`, and ensures `step_ensures` (equality with the spec
  `step` on the views), `exec_wf`, `jar_in_range` and `now_in_range` of the
  result, and `next_id` grown by at most one. It takes the state by value, so
  no state is copied. Each helper (`handle_message_exec`,
  `navigate_tab_exec`, `storage_call_exec`, `set_item_exec`,
  `reply_frame_exec`, `lock_of_url_exec`, ...) is proven equal to the spec function
  of the same name, so the proof is a chain of those equalities, and the
  lookups are loops with invariants (no recursion that a renderer could make
  deep).

  fn urls(&self) -> UrlFns` and three exec methods (`origin_of`, `path_of`,

### 2.13 Navigation with the real URL parser (S)

Instantiate 2.10's URL-to-origin parameter with 2.6's `url_origin` over
1.10's basic URL parser, so `OpenTab` and `Navigate` parse the URL string in
the kernel. Proof: the exec kernel equals the spec with that instantiation,
as `host_parser_full` did in 1.9. The theorems of 2.11 then hold for the
shipped kernel without change, because they were proven for every
instantiation.

**As built (`clazel-kernel` stays at `tier = 2`):** `src/urls.rs` (spec),
`src/exec/real_urls.rs` (exec), `src/real_theorems.rs`,
`src/url_mutation_lemmas.rs`, `tests/conformance_urls.rs`.

- **Where it lives, and why.** In `clazel-kernel` itself, not a new crate. The
  kernel already depends on `clazel-url`, `clazel-origin`, `clazel-cookie` (for
  `narrow`) and `clazel-encoding`; the parser, serializers and origin know
  nothing of the kernel; and nothing of the kernel proof (`spec`, `invariant`,
  `theorems`, ...) imports the new modules, so the dependency runs one way: the
  proof is over the parameter `UrlFns` / `UrlFnsExec`, and `urls` and
  `exec::real_urls` are its one instantiation. A crate of their own would add a
  `Cargo.lock` row and an interface to keep, for no separation the modules do
  not already give. (2.15's `clazel` depends on `clazel-kernel` for `step_real`.)
- **The spec** (`urls::real_urls() = urls_with(real_domain_parser())`, the domain
  parser being `clazel-idna`'s through `clazel_url::url::contract::url_domain_parser`,
  as `host_parser_full` joined it in 1.9). With `parse_absolute(dp, s)` the
  basic URL parser (§4.4) on `s` with no base:
  - `origin_of(s)`: `parse_absolute` then URL §4.7 `url_origin(url, dp, 0)`;
    **`None` if `s` does not parse** (so an `OpenTab`/`NavigateTab` is ignored and
    a `Navigate` gets `error_bad_url`). The opaque id `0` is never read: the kernel
    replaces any opaque origin with the renderer's id (`lock_of_origin`).
  - `path_of(s)`: `narrow` of `url_path_serializer(url.path)` (the octets of the
    URL path serializer's output, so the path and not the query or fragment);
    **the empty path if `s` does not parse**. The kernel reads it only for a URL it
    committed, which parsed.
  - `resolve(base, input)`: parse `base` with no base, parse `input` with that
    as base, and serialize the result with exclude fragment false (URL §4.5);
    **`None` if the base does not parse, or the input does not parse against
    it**.
- **Scalar values.** The parser's precondition is "a scalar value string", but
  the kernel's functions are total on `Seq<u32>`. A string with a surrogate or a
  code point over U+10FFFF fails every function like a parse failure (the guard is
  the first test of each exec method). The text the kernel gets is decoded from
  UTF-8 (2.3), so the guard never fires on real input.
- **`urls_resolve_scalar` (the obligation 2.12 left)** is proven for
  `real_urls()` and for `urls_with(dp)` for every domain parser
  (`lemma_urls_with_resolve_scalar`, `lemma_real_urls_resolve_scalar`), **by
  construction, not by an argument about the parser**: `resolve` returns
  `None` rather than a result that is not a scalar value string. That the
  guard is vacuous, i.e. that the serialization of a parsed URL is always a
  scalar value string (true because the parser percent-encodes or punycodes
  every non-ASCII code point), is a property of all of `clazel-url` and
  `clazel-idna` that is **not proven here**. I looked for a counterexample and
  found none: `tests/conformance_urls.rs` runs every input of
  `urltestdata.json` (896) and 2000 random hard inputs (non-ASCII, controls,
  percent signs, brackets, IDNA and IP literals) through `RealUrls::resolve` and
  `path_of` and checks that the guard never fires (2896/2896). The same holds of
  `path_of`'s `narrow`, which is exact only on ASCII: the path serialization is
  ASCII on all of them. Proving both would be a new invariant over the 20 parser
  states and the host parser; it is left as a gap and nothing else depends on
  it (the isolation theorems hold for every `UrlFns`, guarded or not).
- **The exec** `RealUrls` implements `UrlFnsExec` with `urls() = real_urls()`:
  each method is `all_scalar_values` (proven equal to the spec's quantifier)
  followed by `basic_url_parser`, `url_origin_exec`, `url_path_serializer` and
  `ParsedUrl::serialize`, and its `ensures` is the trait's. 8 obligations,
  first try.
- **For 2.15 (host shell):** call `clazel_kernel::exec::real_urls::step_real(s:
  StateRecord, e: &EventRecord) -> (StateRecord, Vec<OutputRecord>)`: `step_exec`
  with `RealUrls`, proven to meet `step_ensures(psl(), real_urls(), ..)`
  under `step_requires(real_urls(), ..)`. The host's obligations are those of
  2.12 (state from `init_record`, a `Tick` time in range, a URL in an `OpenTab` or
  `NavigateTab` that is a scalar value string, `next_id` below `u64::MAX`); the
  `urls_resolve_scalar` conjunct is now discharged.
- **The theorems.** `real_theorems.rs` states the 2.11 theorems at `(psl(),
  real_urls())`: `corollary_real_reply_only_to_sender`,
  `_lock_is_committed_origin` (with `lock_set_only_by_navigation`),
  `_cookie_confidentiality`, `_cookie_integrity`, `_storage_same_origin` and
  `_cookie_noninterference`. Each is the generic theorem applied, with no new
  proof; 2.10 and 2.11's specs and contracts are unchanged.
- **Conformance** (all through `step_real`, so through the codec and the proven
  parser): the kernel suites of 2.12 now run on the real URL functions instead of
  `TestUrls`, which is gone: WPT `cookies/` 11/11 and 166/167 (the same 1
  expected failure), WPT `webstorage/` 24/24, `cookie_store` differential
  3000/3000. New: WPT `urltestdata.json` navigation, the 336 rows with a base:
  the kernel opens a tab on the base, the renderer sends `Navigate` with the
  input, and the kernel commits exactly the row's `href` (274 rows) or answers
  `Error { code: 3 }` (the 62 failure rows), 336/336; `origin_of` and `path_of` on
  the 560 rows without a base against the row's `origin` and `pathname`,
  560/560; and the guards test above, 2896/2896. `tests/behaviour.rs` gained

- **Mutations:** 16 of 16 are certified kills (the 9 of 2.11 and 7 new on

### 2.14 Sandbox policies (M)

`clazel-sandbox`, safe code only, policies as data:

- Linux: the seccomp-BPF program, generated from a syscall allowlist (read
  and write on the inherited socket, `exit_group`, memory management, futex;
  nothing that opens, connects or forks), for x86-64 and aarch64, checking
  the architecture field first; the Landlock ruleset (no filesystem access
  at all); the namespace set (user, mount, PID, network, IPC).
- macOS: the Seatbelt SBPL profile, `(deny default)` plus the minimum to run.

Tier 1: Kani proves the generator panic-free, and a harness runs every
generated program in a small cBPF interpreter (written from the kernel's
`Documentation/userspace-api/seccomp_filter.rst` and
`Documentation/networking/filter.rst`) on **every** syscall number below
1024 for both architectures, plus a wrong architecture, and checks it
allows exactly the allowlist. That is exhaustive, so not merely bounded.
The interpreter itself is in the TCB (it models the OS), which is why this
crate targets Tier 1 rather than a Verus spec of BPF. The SBPL text is
checked only by the integration tests in 2.16.

Applying these policies is 2.15 and **waits on 2.0**; writing them does
not.

**As built:** `clazel-sandbox` (no dependencies, no `unsafe`, no system
calls), at **Tier 1**. `syscalls.rs` holds the allowlist (22 syscalls, each
with the reason the renderer needs it; nothing that opens, connects, forks,
executes or passes descriptors, so `sendmsg`/`recvmsg`, `clone` and
`rt_sigaction` are absent) with numbers for x86-64 and aarch64, and the
`AUDIT_ARCH_*` values. `seccomp.rs` generates the program: load `arch`,
kill the process unless it matches, load `nr`, one `jeq` per allowed number,
kill, allow; it is defined pointwise (`insn_at`) and refuses more than 255
numbers (8-bit jump offsets). `interp.rs` is the cBPF validator and
interpreter, written from `filter.rst` and `seccomp_filter.rst` (it is in
the TCB). `landlock.rs` handles every filesystem, TCP and scope right and
adds no rule, with `for_abi` to drop rights newer than the running kernel;
`namespaces.rs` lists user, mount, PID, network, IPC with their `CLONE_NEW*`
flags; `seatbelt.rs` renders `(deny default)` plus a minimal allow set. Kernel
numbers and constants are not from memory: the Linux v6.12 tables, headers and
documents are vendored in `vendor/linux/` (commit in `SOURCE.md`), and
`tests/vendored.rs` re-derives every syscall number and constant from them.
Kani harnesses (`proofs.rs`): the generator is panic-free, produces a valid
program and allows exactly the list, for symbolic allowlists of 0 to 3
numbers; the real allowlist on each architecture allows exactly the list for
**every** 32-bit syscall number (a superset of "below 1024") and kills every
other architecture value; the validator and interpreter never panic on any
program of up to two instructions. `tests/policies.rs` repeats the
below-1024 sweep for both architectures, wrong architectures and x32 numbers
as plain tests. Limits: Kani proves the pointwise generator, not the `Vec`
collection in `generate` (CBMC ran out of memory modelling it); selection is
by number only, with no argument filters; the interpreter's rejection rules
are the conservative reading of `filter.rst` because `kernel/seccomp.c`
is not vendored; the SBPL profile is unchecked until 2.16. The seccomp
harnesses for the real allowlist take about nine minutes each.
`xtask`'s Kani step passed `--locked`, which Kani 0.68 rejects; it was never
exercised before this crate had harnesses, so the flag is dropped.

### 2.15 Processes: host shell and renderer stub (M) — ready

`clazel` (the kernel host) creates a socket pair per renderer, spawns
`clazel-renderer` with one end as its stdin, and keeps a table from socket
to renderer id. Its loop reads a frame, calls the proven `step` with the
renderer id of the socket it came from, writes outputs, and spawns or kills
processes as told. A renderer that sends a frame over `MAX_FRAME`, or closes
its socket, becomes `RendererExited`. `clazel-renderer` enters the sandbox
(through 2.0's chosen mechanism) as its first act, before reading a byte,
then waits for `Commit` and runs its script: a list of document.cookie and
localStorage operations, printing each result.

The host shell calls `clazel_kernel::exec::real_urls::step_real`, the exec
`step` with the real URL parser (2.13), not `step_exec` with a URL
implementation of its own; its guarantee for the real parser is
`clazel_kernel::real_theorems`.

Both are Tier 0. Keep the host shell under 300 lines; its line count is in
the README table.

**Notes for whoever picks this up** (collected from 2.0 and 2.10 to 2.14):

- **Entering the sandbox, Linux.** `clazel-sys` exposes `set_no_new_privs()`,
  `unshare(Namespaces)`, `landlock_deny_filesystem(u64)` and
  `seccomp_set_mode_filter(&[SockFilter])`; `clazel-sandbox` builds the
  policy (`seccomp::renderer_program(arch)`,
  `namespaces::renderer_unshare_flags()`, `landlock::RENDERER.for_abi(abi)`), and
  the renderer maps between the two (the BPF instructions to
  `clazel_sys::linux::SockFilter`, the `u32` flags to a `Namespaces` built from
  its constants). Order: `set_no_new_privs` first (both seccomp and
  Landlock need it, see the `clazel-sys` audit in `docs/SYS-AUDITS.md`), then
  `unshare`, then Landlock, then seccomp last, since its allowlist forbids the
  calls before it.
- **Stay single-threaded.** The seccomp filter covers only the thread that
  installs it and threads created afterwards (no `TSYNC`), `unshare(USER)`
  fails in a multithreaded process, and the allowlist has no `clone` or
  `clone3`, so the renderer must start no thread at all, before or after.
  Rust's standard library starts none on its own.
- **Landlock ABI.** `clazel-sys` passes the ABI 1 `landlock_ruleset_attr` (the
  filesystem rights only) and cannot ask the kernel for its ABI version
  (`LANDLOCK_CREATE_RULESET_VERSION` is not wrapped). So: try the newest
  filesystem rights and fall back to older ones on `EINVAL`, or add a version
  query to `clazel-sys`, which is a change to that crate and needs a new audit
  by another session (CLAUDE.md rule 1). `clazel-sandbox`'s TCP and scope
  rights cannot be applied through `clazel-sys`; network access is denied by
  the seccomp allowlist (no `socket`, `connect`, ...) and the network
  namespace.
- **macOS:** `clazel_sys::macos::sandbox_init_profile(&seatbelt::renderer_profile())`.
- **Fail closed:** any `Err` from any layer means the renderer exits before
  reading a byte, with a message saying which layer failed; the host reports
  it.
- **What the kernel expects of the host** (`src/contract.rs`): start from
  `init_record()`; call `step_real` (above) for every event; take the renderer
  id from the socket a frame arrived on, never from the frame; keep `next_id`
  below `u64::MAX` and give `Tick` times in range (`step_requires`); carry
  out the outputs in order (a cross-origin navigation is `Kill`, `Spawn`,
  then `ToRenderer(Commit)` to the new renderer, which is the one exception
  to replying only to the sender). Scripts come only with `OpenTab` and
  `NavigateTab` (user events); a renderer's own `Navigate` commits an empty
  script. A malformed frame, or one with a kernel-only message, makes the
  kernel answer `Kill`. Frames are `clazel-ipc`'s: `MAX_FRAME` is 1 MiB and
  `payload_length` lets the host refuse an oversized frame from its first 4
  bytes, which becomes `RendererExited`.
- **Script format:** the plan leaves it open. Keep it trivial and decode it
  with code that is either proven or obviously total; the script comes from
  the user's `OpenTab` through the kernel, not from a web page.
- **The README line count of the host shell** that this item promises is not
  measured by `cargo xtask report` today; adding it is part of this item.

**As built:** `crates/clazel` (the host shell, a library `Host` and a binary)
and `crates/clazel-renderer` (library and binary), both Tier 0 with std and
workspace crates only (no new third-party package, so `Cargo.lock` gained two
workspace rows and DEPENDENCIES.md none).

- **Host** (`crates/clazel/src/lib.rs` and `main.rs`, 298 lines by `wc -l`; 2.16 moved
  `main.rs` to `cli/` and the count is now `src/` alone, 278;
  the README footnote reports the number and `cargo xtask report` fails over
  300). `Host::new(command)` starts renderers with `command(id)`;
  `open_tab` and `navigate_tab` are the user's `OpenTab` and `NavigateTab`
  (a `Tick` with the wall clock, in seconds since 1601, goes before every
  event); `pump` and `run` handle what the renderers' sockets report.
  Per renderer: `UnixStream::pair`, the child end given to the process as
  both stdin and stdout (so the renderer needs no `unsafe` to get a
  socket), stderr piped, and one reader thread per socket that reads whole
  frames and sends `(id, frame)`, with the id the socket was created for.
  A frame announcing more than `MAX_FRAME` is refused from its first 4
  bytes (`payload_length`), and a closed socket ends the thread; both make
  the host reap the process and feed the kernel `RendererExited`. Outputs of
  `step_real` are carried out in order. Events from a renderer the host no
  longer has (killed, or replaced by a navigation) are dropped. The host
  stops calling `step` if `next_id` reaches `u64::MAX`. A write to a socket
  times out after 5 s. Every frame the host carries is printed decoded
  (`renderer 0 -> document.cookie = "a=1"`, `renderer 0 <- result "a=1"`),
  and so is each exit with the process's status and stderr; `Host::log`
  keeps the lines. `clazel URL SCRIPT` opens one tab and runs it; 2.16 added
  `clazel demo`.
- **Where results are printed.** The renderer prints nothing: the host sees
  every request and reply on the socket, which is the one channel the kernel
  also reads, so it prints the results. (A renderer-to-host result channel
  would be a message the schema does not have and the kernel would treat as
  malformed.)
- **Renderer.** `sandbox::enter` is the first call in `main`, before a byte
  is read; any `Err` prints `clazel-renderer: sandbox layer \`<name>\`
  failed: ...` and exits 71, which the host reports with the stderr text.
  macOS: `sandbox_init_profile(&seatbelt::renderer_profile())`. Linux:
  `set_no_new_privs`, `unshare` (the five namespaces of
  `namespaces::RENDERER`), Landlock, seccomp last, with the BPF program
  mapped to `clazel_sys::linux::SockFilter`. Landlock tries the filesystem
  rights of ABI 5, 3, 2, 1 in turn and moves on only on `EINVAL`; any other
  error (Landlock disabled, `ENOSYS`) fails closed. `clazel-sys` is
  unchanged. No thread is started.
- **Script format.** UTF-8 lines: `cookie-get`, `cookie-set <string>`,
  `storage-get|storage-remove <key>`, `storage-set <key> <value>`,
  `storage-clear`, `storage-key <n>`, `storage-length`; blank lines and
  `#` comments ignored. The decoder (`script.rs`) uses no indexing and no
  unchecked arithmetic. A bad line exits 64 naming the line. Because the
  schema has no reply to a cookie write, `removeItem` or `clear`, and
  answers `setItem` only with an `Error`, the stub sends a `StorageLength`
  after each `setItem` as a barrier so that replies cannot be mistaken for
  each other.
- **Tested.** Renderer: 3 script tests, 3 protocol tests over in-memory
  streams, and `tests/sandbox.rs` (a harness-less test that re-runs itself
  as a child, enters the real sandbox, and checks that `open` and a TCP
  `connect` fail): on this Mac, `sandboxed=true`. Host (`tests/host.rs`,
  7 tests, all ignored under Miri): oversized frame, closed socket and a
  kernel-only message each end in `RendererExited` or `Kill` and the kernel
  forgets the tab (a later navigation spawns nothing); two stubs show that
  replies go only to the sender (a frame has no id); a same-origin
  navigation commits to the same renderer and a cross-origin one is
  `Kill`, `Spawn`, `Commit`; the real sandboxed renderer runs a cookie and
  `localStorage` script end to end on macOS arm64, and a bad script is
  reported with its stderr.
- **Limits.** The Linux path (`sandbox.rs`, namespaces, Landlock fallback,
  seccomp) was written on a Mac and has not been compiled or run: CI on
  Linux is its first test. The Linux tests accept a renderer that fails
  closed with a sandbox-layer message (a container may refuse `unshare` or
  Landlock) but never a renderer that runs unsandboxed. There is no
  `pivot_root` to an empty root (`clazel-sys` has no such call): the
  filesystem is denied by Landlock, not hidden. The Seatbelt profile worked
  unchanged for this script. The README table has no rows for the two crates
  until `cargo xtask report --write` is run where Verus and Kani are
  installed.


### 2.16 Exit demo and adversarial tests (M) — built, macOS only

- `cargo run -p clazel -- demo`: two tabs, `https://a.test/` and

**Notes for whoever picks this up:**

- **The hostile renderer is killed on its first malformed frame** (2.10), so
  "sends random frames for a fixed time" becomes: spawn many short-lived
  hostile renderers, each sending one random or mutated frame, and check that
  each is killed, that the kernel never crashes or replies to another
  renderer, and that the well-behaved renderers' results are unchanged.

  needs a decision by the maintainer before the tests go into CI: relax the

  fail-closed to get CI green.

  says so. Two public fields were added to `Host` for the tests: `state` (the
  conformance test preloads the cookie jar, as the kernel's test does, because

  `None` is the wall clock).
- **Hostile renderer.** `clazel-renderer` gained `hostile.rs` (a SplitMix64
  generator and `generate(seed)`: one frame per seed, of one of eight kinds:
  truncated, oversized, non-shortest CBOR, CBOR outside the profile and
  unknown message tags, invalid UTF-8, random bytes, a mutated valid
  message, a kernel-only message) and the binary `clazel-adversary` (enters the
  sandbox first, like the real renderer; `hostile SEED` sends the frame and
  waits to be closed). Every generated frame is checked against the real decoder
  to be one the kernel must refuse; a unit test checks 4000 seeds.
  `tests/adversarial.rs` runs 96 sandboxed hostile renderers and 16 sandboxed
  well-behaved ones against one kernel at once, from one printed seed
  (default `0x2026_1023`, `CLAZEL_SEED=n` to reproduce or vary). It checks that
  every hostile renderer ends the way its kind says, with its seed, kind and
  first bytes in the host's `exited` line (its stderr); that the kernel sent
  it nothing but its `Commit`; that the kernel forgot all 112 tabs; and that
  each well-behaved renderer's log is identical to its log when the 16 run
  alone. Passes on the default seed and on seeds 1, 2, 3, 99, 12345 and
  777777; all eight kinds appear in each run. No crash of the host or kernel
  was seen.
- **Sandbox escape attempts.** `escape.rs` (std only) and `tests/escape.rs`
  in `clazel-renderer`: from a sandboxed `clazel-adversary`, open the cookie
  jar's would-be file (a real file the test writes), open `/etc/hosts`, create
  a file, connect to a TCP listener, listen on a TCP port, bind a UDP socket,
  connect to and create a Unix socket, and run `/bin/echo` (`Command`, so
  `posix_spawn`/`execve`). Each attempt first runs unsandboxed and must
  succeed, so a denial is the sandbox's. **macOS (run): 9 of 9 return
  `Operation not permitted (os error 1)`** under the unchanged Seatbelt
  profile. **Linux (written, not run):** the test passes only if the process
  dies of `SIGSYS`; an error return fails it, and so does a renderer that
  fails closed before the call, because then nothing was tried.
  **Not expressible without a `clazel-sys` change:** `fork` and `ptrace` of a
  sibling. `std` has neither (`Command::spawn` is `posix_spawn` on macOS and
  fork or clone plus exec on Linux, so on Linux the `execve` attempt does
  exercise process creation, but a bare `fork` and `ptrace` are not
  attempted anywhere), and `clazel-sys` wraps neither. Adding them is a change
  to `clazel-sys` with its own audit by another session (CLAUDE.md rule 1),
  not done here; no `libc` or `unsafe` was used elsewhere to get around it.
- **WPT `cookies/` end to end.** `clazel`'s `tests/conformance_wpt_cookies.rs`

- **CI and user namespaces (decided 2026-10-24 by the maintainer: option
  (2), the AppArmor profile).** `packaging/apparmor/allow-userns.sh` installs
  a profile granting `userns` and nothing else to the named programs; CI's
  base and crate jobs run it for the test binaries before the tests, and the
  release tarball's `install.sh` runs it for the installed renderer. Not yet
  seen passing in CI. The text below is the analysis it was decided on. On `ubuntu-24.04`
  unprivileged user namespaces are restricted by AppArmor
  (`kernel.apparmor_restrict_unprivileged_userns=1`), the renderer's
  `unshare` layer fails, and it fails closed (exit 71, `sandbox layer
  \`namespaces\` failed`). Then these tests fail on Linux CI: all 9 escape
  tests, the adversarial test, the WPT test and the demo test (the 2.15 host
  tests accept a fail-closed renderer on Linux, these do not: a test that
  cannot reach the renderer's code proves nothing). Options: (1) a CI step
  `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` before the
  tests: one line, covers all binaries, but changes the runner for every job
  and a real user's machine would not have it; (2) an AppArmor profile that
  grants the `userns` permission to `clazel-renderer` and `clazel-adversary`
  only (the mechanism Ubuntu uses for browsers), loaded with `apparmor_parser`
  before the tests: scoped to the two binaries, and what a package would have
  to ship anyway, but more to write and its path is the CI build directory;
  (3) treat the user namespace layer differently, such as running without it
  where the kernel refuses it: this weakens fail-closed and the defence in
  depth the plan relies on, and is not recommended. **Recommended: (2);**
  (1) if the profile proves too fiddly for CI. Fail-closed stays as it is in
  any case.

## Risks

- **Verus on noninterference.** Map-valued state and trace induction are
  heavier than anything in Phase 1. Mitigation: keep the unwinding lemmas
  per event kind, keep the jar a sequence with a root-indexed view proven
  equal to it, and prove the trace theorem from the three lemmas only.
- **6265bis is a draft.** It may change before it becomes an RFC. The spec
  is pinned to one revision; moving to the RFC is a re-transcription with a
  diff, like any standard update.
- **The PSL changes weekly** and is large (about 10 000 rules). Pin a
  commit and regenerate deliberately. Large tables already worked in 1.8.
- **A boundary stated wrongly.** Stating isolation by registrable domain, or
  keeping a global cookie limit, makes the headline theorem false (2.9).
  The plan states both choices; if Verus later finds another flow the RFC
  allows, the theorem's condition must be narrowed in the open and said so
  here, never the proof weakened.
- **Linux sandbox availability.** Landlock needs Linux 5.13 or later, and
  some distributions block unprivileged user namespaces. Renderers fail
  closed, so on such systems the browser does not run renderers at all
  until the user changes the setting; that is a usability cost, accepted.
  CI's `ubuntu-24.04` runner may be one of them: see 2.16's notes.
- **macOS `sandbox_init` is deprecated** and SBPL is undocumented. Chromium
  and Firefox depend on it too, so removal would be widely noticed, but the
  plan has no fallback beyond option C's `sandbox-exec`, which is just as
  deprecated.
- **The host shell is trusted and unproven.** Its one duty (socket to
  renderer id) is checked by the hostile-renderer test, not proven. Keep it
  small enough that this stays credible.
- **WPT `cookies/` mostly needs a server.** Only the data-shaped tests run
  in Phase 2; the rest join in Phase 3, and the README shows the count
  honestly in the meantime.
