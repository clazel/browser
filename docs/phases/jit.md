# The JavaScript JIT (part of Phase 7), detailed plan

**Status: proposed (2026-11-16). Nothing is built.** Decided by the
maintainer on 2026-11-16:
- JavaScript runs mainly through a JIT, with no interpreter-only stage;
- the JIT targets Windows and x86-64 from the start, alongside macOS arm64.

Item J.0's decisions were taken by the maintainer on 2026-11-16, every
recommendation as written. The rest of Phase 7 is planned in
[phase-7.md](phase-7.md), whose "Shapes fixed here for the JIT" section
fixes what item J.1 lists.

**Goal:** JavaScript runs as machine code the browser generated, on x86-64
and on A64 (64-bit Arm).
- **Safety, proven before anything runs:** generated code cannot touch
  memory outside the regions it was handed, and cannot jump anywhere but its
  own instructions and its one exit.
- **Correctness, proven op by op:** the code does what the bytecode
  semantics says.
- **Wasm reuse:** the machine-code half of the work is built so that a
  WebAssembly front end can reuse it unchanged (see "Looking ahead").
  WebAssembly itself is not in this plan.

The **baseline JIT is the main path.** A thin interpreter remains, built
from the same op handlers the JIT's exits call, for four uses:
- code that runs once, before it is worth compiling;
- a full code cache;
- the JIT-off mode;
- the reference that Test262 runs with the JIT forced on are compared
  against.

It is a dispatch loop over handlers that exist anyway, not a separate
engine.

*Exit:*
- **Platforms:** on Windows x86-64, Linux x86-64 and macOS arm64, a page's
  functions run through the baseline JIT, and every code blob passes its
  instruction set's tier 2 validator before it is mapped executable.
- **Suites:** Test262 gives the same results with the JIT on, forced on
  and off.
- **Benchmarks:** a stated set is measured against the JIT-off mode, and
  the result is reported, not asserted.

Linux aarch64 and Windows arm64 follow from the same crates. They need CI
runners, and are in "Looking ahead".

Nothing here speculates on types, inlines across functions, allocates
registers globally or patches code it has already validated. An optimizing
tier is in "Looking ahead".

A convention for this file, as in phase-5.md: a section number marked † was
written from memory, not read at a pinned commit. It must be checked against
the commit a spec header pins before that header cites it.

## Why this shape

A proven optimizing JIT for JavaScript is a research problem. A machine-checked
proof covers speculation and deoptimization only for toy languages (CoreJIT,
Barrière et al., POPL 2021). Production JITs have proven pieces, such as range
analysis (Vera) and CacheIR code generators (Icarus), not the whole. Two
results show what is achievable now:

- **Validating the output instead of proving the compiler** (NaCl's
  validator; VeriWasm, NDSS 2021). A small checker reads every blob of
  generated code and refuses it unless it stays inside its sandbox. Memory
  safety then depends on the checker, not on the compiler. That is how this
  repository already works: trust a small proven thing, not a large clever one.
- **Per-template proofs for a non-optimizing JIT** (Jitk, OSDI 2014;
  Jitterbug, OSDI 2020, for the Linux BPF JITs, which cover both x86-64
  and arm64). Each bytecode op lowers to a fixed instruction sequence, and
  each sequence is proven to simulate its op. Composition is then one lemma.

So there are two layers, shipped in this order:

1. **Safety (tier 2, required before any generated byte runs):** one
   validator per instruction set, each proving the same theorem. Together
   they make the one `unsafe` entry into generated code sound, whatever the
   compiler does.
2. **Correctness (target tier 2, may trail the code):** the front end and
   each back end refine the bytecode semantics. A gap here is a wrong answer
   inside the page's own sandbox, never a memory error. It is listed as such
   until it is proven.

## Exit criteria

Done when all of these hold:

1. **Tiers:**
   - `clazel-x64` and `clazel-a64` (instruction-set specs, encoders and
     decoders) at **tier 2**;
   - `clazel-codecheck` (both validators) at **tier 2**;
   - `clazel-lir` at **tier 2**;
   - each with mutations, conformance and an independent transcription;
   - `clazel-jit` (back ends and JS front end) at **tier 2** if J.9 and
     J.10's proofs went through. Otherwise it stays at its real tier, and
     the README says which ops are proven on which instruction set.
2. **The validator's theorem** (J.6). It is stated once, over an abstract
   machine interface, and proven for each instruction set's semantics:
   every execution of an accepted blob, started at an accepted entry with the
   context invariant,
   - only loads and stores inside the regions it was handed;
   - leaves only through the exit sequence;
   - executes no system or privileged instruction;
   - does not write the reserved registers or the stack pointer, except in
     the fixed prologue and epilogue;
   - never runs past its end.
3. **ISA evidence** (J.3, J.4):
   - each semantics is transcribed twice, from independent sources, and the
     two are proven equal on the subset;
   - running every instruction template on real hardware, over generated
     and boundary inputs, matches the spec bit for bit (x86-64 on the Linux
     and Windows runners, A64 on the macOS runner);
   - each decoder matches a reference disassembler on every encoding in
     the subset, plus random bytes. The reference disassembler is a test
     dependency only.
4. **Suites:** Test262 with `--jit=always` gives exactly the `--jit=off`
   results on all three platforms, with failures listed by name.
5. **Sandbox** (J.8). On every OS, no page in the renderer is ever both
   writable and executable.
   - **Linux:** the renderer never makes memory executable after start-up.
     Its code region is mapped RX once, before the seccomp filter goes on,
     from a sealed `memfd` that only the validating side can write, and the
     filter refuses `PROT_EXEC` on every later `mmap` and `mprotect`.
   - **Windows:** the renderer keeps `PROHIBIT_DYNAMIC_CODE` (Arbitrary
     Code Guard). Validated code is mapped into it by a separate code
     process (J.0(b)).
   - **macOS:** `MAP_JIT`, the per-thread write-protect switch and the
     `allow-jit` entitlement.
6. **Hostile tests**, per instruction set:
   - blobs assembled by hand to escape are all refused: out-of-region
     loads, jumps into the middle of an instruction (x86-64), prefixes that
     change an instruction's meaning, `syscall`/`svc`, writes to the context
     register, self-modification;
   - a fuzzer that mutates accepted blobs finds no accepted blob that faults
     outside its regions when run under a guard-page harness.
7. `scripts/verify.sh` exits 0 and CI's full verification is green on the
   three platforms. Every `clazel-sys` change has an audit row by another
   session (rule 1).

## What is proven, and what is assumed

1. **Proven (Verus):**
   - per instruction set, the encoder and decoder are inverses on the
     subset;
   - the validator's theorem, for each instruction set;
   - LIR's semantics is deterministic, and its typing rules hold;
   - per op, the JS front end's lowering refines the bytecode `step`;
   - per LIR instruction and per instruction set, the back end's template
     refines LIR's semantics;
   - composition over a whole function.
2. **Assumed, and listed in VERIFICATION.md's TCB:**
   - each instruction-set semantics is faithful to the hardware for the
     instructions its validator accepts. The evidence is the independent
     transcription, the hardware differential tests and the decoder
     differential;
   - the enter stub in `clazel-sys`, its audit and its tests;
   - the OS's page protections and cross-process mapping;
   - the code process (J.0(b)): it maps only what passed validation, but its
     handle to the renderer is a capability, so it is small, sandboxed and
     audited like `clazel-sys`'s callers;
   - instruction-cache coherence: x86-64 needs only a serializing jump after
     the mapping changes; A64 needs `dc cvau`, `ic ivau` and `isb`, or the
     OS call that does them.
3. **Not covered, and said so:**
   - Spectre-style speculation. A blob that is architecturally confined can
     still leak its own process's memory through a side channel. The defence
     is the existing process-per-site model.
   - Timing and performance.
   - Correctness of any op the README lists as unproven.

## Design choices that keep WebAssembly in mind

Each choice is made for JS and also makes a Wasm front end a small
addition rather than a second JIT.

- **One low-level IR, LIR, shaped like Wasm.**
  - Control flow is structured (`block`, `loop`, `if`, `br`, `br_if`,
    `br_table`) with no arbitrary goto.
  - Values are typed `i32`, `i64`, `f64` (later `f32`).
  - Memory is accessed only through **regions**, each with a base and a
    bound, and every access names its region.

  A JS op lowers to a short LIR sequence, a Wasm instruction almost one to
  one. Each instruction set's back end consumes LIR, so a third instruction
  set is one more back end and one more validator.
- **Regions are the only memory.** A blob is entered with a context register
  pointing at a fixed table of (base, bound) pairs:
  - JS: the value stack (frames), the object arena, the inline-cache data and
    the constant pool;
  - Wasm later: linear memory, globals and tables.

  Every load and store is `base + checked index`, with an explicit bounds
  check. There are no guard-page tricks, so a proof never relies on a
  4 GiB reservation (Windows reserves address space differently anyway).
  Indexes are masked after the check, which also blunts Spectre v1 within a
  region.
- **No indirect branches, so x86-64 needs no bundles.** Every jump is direct,
  or is the fixed exit. The validator therefore finds every instruction
  boundary in one linear decode from the blob's start, and rejects any direct
  target that is not one of those boundaries. Unlike NaCl, no
  aligned-bundle rule is needed: nothing can jump to a computed address in
  the middle of an instruction. `br_table` lowers to a bounded sequence of
  compares and direct jumps, never to a jump table.
- **Generated code never calls anything.** A runtime service (allocation,
  a slow property path, a GC point, a call to a native DOM function, and for
  Wasm a host call, `memory.grow` or a trap) is an **exit**. The code stores
  an exit code and its operands in the context and returns to the enter stub.
  Rust does the work and re-enters at a recorded resume point. So Rust is
  never called from generated code, there are no function pointers to
  Rust, and nothing unwinds through generated frames, which matters on
  Windows, where unwinding needs registered unwind tables. Regions are passed
  afresh at each entry, so the arena may grow or move between entries.
- **Code is immutable once validated.** Inline caches are **data** (shape id,
  slot index) in a region that the code reads. There is no stub patching, so
  each blob is validated, and on Windows mapped, exactly once.
- **The JIT's frames are the interpreter's frames.** JS frames live in a
  value-stack region with one layout. Baseline code keeps every bytecode
  register in its slot at op boundaries. Moving between the interpreter and
  the JIT, either way, is a jump with no state translation. That covers
  on-stack replacement, an exception, and "this op is not compiled".
  JS-to-JS calls push frames in the region and never use the native stack,
  so the native stack depth of an entry is a constant the validator checks.
- **Values are one `u64` (NaN-boxed)** with heap references as arena
  indexes. JS and Wasm share LIR's `i64` and `f64`, and the boundary
  converts without allocating.
- **One calling convention of our own.** The enter stub is the only code that
  meets the platform ABI: System V on Linux and macOS x86-64, Microsoft x64
  on Windows, AAPCS64 on A64. Inside a blob, the register assignment is
  ours and is the same on every OS for a given instruction set. The ABI
  differences are confined to the audited stub.
- **The instruction-set layer knows nothing of JS.** `clazel-x64`,
  `clazel-a64`, `clazel-codecheck`, `clazel-lir` and the back ends take no
  JS-specific type. `cargo xtask check` can enforce that through their
  dependency lists.

### J.0 Decisions for the maintainer (S): decided

**Decision (2026-11-16), by the maintainer: every recommendation below is
taken.** That is:
- (a) **E1:** one `enter` function in `clazel-sys`, taking a `Validated`
  value only `clazel-codecheck` can build. CLAUDE.md rule 1 and
  `xtask/src/sys.rs` gain the code-entry category in the same pull request
  as J.7, the first code that uses it, not before. That `clazel-sys` change
  is audited by another session.
- (b) **C2:** the renderer never makes memory executable on Windows or
  Linux. On Windows a code process maps validated code into the renderer,
  which keeps Arbitrary Code Guard. On Linux the code region is mapped RX
  before the seccomp filter goes on. macOS uses `MAP_JIT` in the renderer.
- (c) **G1:** the JIT is on by default once both validators are at tier 2.
- (d) x86-64 v1 (SSE2) only.

**Added with (b) and the measurements, 2026-11-16, by the maintainer:**
- **Batching is a design requirement**, not a later optimization. A round
  trip to the code process (estimated 10 to 50 µs, unmeasured) costs far
  more than validating a small function (estimated under 1 µs). So the
  renderer sends compiled functions in batches, and it keeps running the
  interpreter loop while a batch is checked and mapped; it never blocks on
  one. J.11 measures the round trip.
- **The validator is measured from the first commit that runs it** (J.6).


**(a) The `unsafe` rule for entering generated code** (CLAUDE.md rule 1 and
`xtask/src/sys.rs` rule 8). Today every call through a function pointer is
rejected, except a dispatcher cast or a vtable slot.
- **E1:** one new category, the **code entry**. It is exactly one function in
  `clazel-sys`, `enter(region: &CodeRegion, entry: Validated, ctx: &mut
  Context) -> Exit`. It holds one `unsafe` block per instruction set and OS
  ABI, which turns the region's base address plus the validated offset into
  an `extern "sysv64" fn` (or `"win64"`, or `"C"` on A64) and calls it. A
  `Validated` value can be built only by `clazel-codecheck`, so the policy
  decision stays in verified code. Each `SAFETY:` comment cites the
  validator's theorem, the ABI document and the OS's W^X documentation.
  `xtask/src/sys.rs` learns the one allowed shape, and the audit checks it.
- **E2:** the same, but the stub is a fixed blob of machine code shipped as
  data and validated like any other.

**Recommendation: E1.** It is a change to rule 1, and the first `clazel-sys`
change under it is audited by another session.

**(b) Who makes code executable**, now that Windows is in from the start.
- **C1: the renderer itself, on every OS.** On Windows this means turning
  off `PROHIBIT_DYNAMIC_CODE` (`appcontainer.rs`), and on Linux allowing
  `PROT_EXEC` in seccomp. It is simplest, and it weakens the sandbox on both.
- **C2: never the renderer, except on macOS.** The renderer compiles and
  sends the bytes to a writer it cannot impersonate. The writer validates
  them with `clazel-codecheck` and makes them executable.
  - **Windows:** a small sandboxed **code process** per renderer, holding
    only a handle to its renderer with the rights needed to map a section
    into it (`MapViewOfFile2`† into the target process, as Edge's
    out-of-process JIT does). The renderer keeps Arbitrary Code Guard.
  - **Linux:** the writer can be a thread of the renderer's own launcher
    before sandboxing, or the code process. It holds the writable view of a
    sealed `memfd` whose executable view the renderer mapped before its
    seccomp filter went on. The filter then forbids `PROT_EXEC` entirely.
  - **macOS:** no other process can map code into the renderer under the
    hardened runtime, so the renderer validates and uses `MAP_JIT` (C1
    there).
  - **Cost:** a process per renderer on Windows, one IPC round trip per
    compiled function, and cross-process mapping calls in `clazel-sys`.

**Recommendation: C2.** It keeps the renderer's sandbox as strong as it is
today on Windows and Linux. The batching of compilations keeps the round
trips off the hot path, and J.11 measures it.

*Later note (2026-11-16):* C2 is the browser's choice, not the engine's.
- Phase 7 makes the engine embeddable (phase-7.md, "The engine as a
  library"), so `clazel-jit` asks a `CodeMapper` to make validated code
  executable.
- C2's code process and code writer are the browser's mapper.
- An in-process mapper (C1's shape, in `clazel-sys`) is there for
  embedders that have no such sandbox. It lands with J.7, under the same
  audit.
- Either way, nothing becomes executable before `clazel-codecheck`
  accepts it.
- `clazel-jit` itself names no process or IPC type.

**(c) Which tier gates shipping.**
- **G1:** the JIT is on by default once both validators are tier 2, with
  correctness proofs following op by op.
- **G2:** off by default until `clazel-jit` reaches tier 2.

**Recommendation: G1.**

**(d) Which x86-64 extensions the subset may use.** Baseline is x86-64 v1
(SSE2) only, so every 64-bit x86 CPU runs it, and the spec has no CPUID
dispatch. **Recommendation:** v1 only. Later extensions (`popcnt`, `lzcnt`,
`BMI`) are a later decision, and each needs a CPUID check outside generated
code.

### J.1 What the rest of Phase 7 must fix in place (S)

- The bytecode semantics is a Verus `spec fn step`, defined before the
  handlers, which refine it.
- Register-based bytecode, with frames in one value-stack region of `u64`
  slots.
- NaN-boxed values, with heap references as `u32` arena indexes.
- Inline caches as data, keyed by a shape id.
- Every op that can allocate, call out or throw is a distinguished op, so it
  maps to an exit.
- The op handlers are plain Rust functions over the frame region, shared by
  the interpreter loop and the JIT's exits.

### J.3 `clazel-x64` (L)

- The subset: 64- and 32-bit integer ALU ops, shifts, `imul`, `cmp`/`test`
  with `jcc`, `cmovcc`, `setcc`; loads and stores with base, index and scale
  plus disp32 only (no RIP-relative, no segment overrides); `jmp rel32`,
  `ret` in the epilogue only; SSE2 scalar double `addsd`/`subsd`/`mulsd`/
  `divsd`/`sqrtsd`/`ucomisd`/`cvt*`, `movq` between general and XMM
  registers.
- A fixed **canonical encoding** per instruction: the encoder emits only it,
  and the validator accepts only it, refusing redundant prefixes, alternative
  ModRM forms and every prefix the subset does not name. The set of accepted
  byte strings is then small enough to enumerate in the decoder differential.
- Semantics as a `spec fn` over registers, flags, RIP and memory as a partial
  map; contracts first (rule 3); encoder and decoder proven inverse.
- Independent transcription from the second source, proven equal on the
  subset.
- Hardware differential tests on the Linux and Windows runners.

*Later note (2026-11-16):* the sources, decided by the user.
- The **primary spec** is transcribed from the ACL2 `x86isa` model.
- The **independent transcription** is made from Intel's SDM, its prose and
  pseudocode (volume 2, pinned in J.2), not from another formal model.
- A **different session** writes the independent transcription, and it does
  not read the primary transcription.
- The **hardware differential tests** are the further check against both.
- The Sail x86 translation (`sail-x86-from-acl2`) is kept only as a check on
  our reading of ACL2. It is a machine translation of ACL2, so **it is not
  independent of it** and does not count as a second source. The crate header
  says so.

### J.4 `clazel-a64` (L)

As J.3. The subset is integer ALU, compare and conditional select, loads and
stores with register base and scaled register or immediate offset, `b`,
`b.cond`, `cbz`/`cbnz`, `ret` in the epilogue only, and scalar double FP. It
has fixed 4-byte words and no prefixes. Hardware tests run on the macOS
runner.

*Later note (2026-11-16):* the sources, decided by the user.
- The **primary spec** is transcribed from the Sail Arm model and Arm's ASL,
  which are one source: the Sail model is a translation of the ASL, which
  Arm's machine-readable specification also carries.
- The **independent transcription** is made from the Arm Architecture
  Reference Manual's prose (DDI 0487, pinned in J.2), not from another formal
  model.
- A **different session** writes the independent transcription, and it does
  not read the primary transcription.
- The **hardware differential tests** are the further check against both.

### J.5 `clazel-lir`: syntax, typing, semantics (M)

- Structured control flow, typed values, region-tagged loads and stores
  with explicit `bounds_check`, and `exit(code, operands)`.
- A `spec fn` semantics, and a typing judgment proven sound.
- The instruction list is checked against the Wasm core instructions a Wasm
  front end would need, and gaps are recorded.

### J.6 `clazel-codecheck`: the validators (L, then M for the second)

- **One theorem statement**, over an abstract interface: decode, step,
  memory access set, control targets. Each instruction set proves it for its
  own semantics.
- Checks, in one linear decode:
  - every instruction is in the subset, in canonical encoding;
  - every direct target is a decoded boundary inside the blob;
  - no indirect branch except the exit sequence;
  - every load and store uses a region base register plus an index register
    that was compared against that region's bound, and masked, earlier in
    the same basic block, by a fixed recognizable sequence;
  - reserved registers and the stack pointer are written only in the fixed
    prologue and epilogue;
  - no system instruction;
  - every path ends in the exit sequence or a branch.
- Independent transcription: a second validator per instruction set, written
  as a dataflow analysis, proven to accept only what the first accepts.
- Hostile corpus and mutation fuzzer (exit criterion 6).
- **Benchmark:** validate a few MB of back-end output (before J.9, of the
  encoders' template output), per instruction set. Report ns per instruction
  and MB/s in the crate's README. The estimate this plan was written
  against is 5 to 20 ns per instruction, roughly a disassembler's speed:
  one linear pass, a table lookup to decode, and per-register state for
  the bounds checks. A result far above it is a design problem, so it goes
  back to J.0 rather than being tuned around.

### J.7 `clazel-sys`: code regions, cross-process mapping, enter (M, after J.0(a), (b))

- **Linux:** `memfd_create`, seals, and two mappings (RW in the writer, RX in
  the renderer before its filter). The cache maintenance is a serializing
  instruction emitted in the stub.
- **Windows:** `CreateFileMapping`, `MapViewOfFile2`† into the renderer from
  the code process, with `PAGE_EXECUTE_READ` there and no writable view in
  the renderer; `FlushInstructionCache`.
- **macOS:** `MAP_JIT`, `pthread_jit_write_protect_np`,
  `sys_icache_invalidate`.
- `enter` per J.0(a), one block per ABI. Tests skip under Miri.
- The session that writes this item does not write its audit row.

### J.8 Sandbox (M)

- **Linux:** seccomp argument filters refuse `PROT_EXEC` on `mmap` and
  `mprotect` (the planned filter noted in `syscalls.rs`).
- **Windows:**
  - the renderer keeps `PROHIBIT_DYNAMIC_CODE`;
  - the code process gets its own AppContainer, and a handle to exactly one
    renderer, created by the host when it spawns both;
  - the escape tests extend to "a renderer cannot map executable memory
    itself" and "a code process cannot reach another renderer".
- **macOS:** the `allow-jit` entitlement, and Seatbelt unchanged otherwise.

### J.9 Back ends: LIR → x86-64 and LIR → A64, with proofs (L each)

- No register allocation: every LIR local is a frame slot, and each LIR
  instruction is a fixed template over scratch registers, so each template's
  proof is local.
- Per-template refinement of LIR semantics, then composition over
  structured control flow, once per instruction set.
- The output always passes J.6, and a test checks that the back end never
  produces a blob the validator refuses.

### J.10 JS front end: bytecode → LIR, with proofs (L)

- One lowering per bytecode op:
  - fast paths inline: small-integer arithmetic with overflow checks, `f64`
    arithmetic, comparisons, branches, property get and set through inline
    cache data;
  - everything else is an exit to the shared handler.
- Proof per op: the LIR refines `step`. This is written once and holds on
  both instruction sets, because it stops at LIR.
- Tiering: compile after N entries or loop back-edges, with entry at a loop
  head through the shared frame. Code that runs once stays in the
  interpreter loop.

### J.11 Code cache, memory bounds, measurement, hostile pages (M)

- Bound the code bytes per renderer. When the cache is full, evict and fall
  back to the interpreter loop.
- Measure the IPC cost of C2 per batch and per compiled function, on
  Windows and Linux, and the break-even point: how many runs before a
  function's compile, validation and mapping cost is repaid. The estimate
  is 30 to 150 runs per function at the baseline tier, which is where the
  tiering threshold N starts.
- Hostile pages: huge functions, deep recursion, inline-cache churn, a flood
  of compilations. None may crash a renderer or exceed its bounds.

### J.12 Status, README, VERIFICATION.md (S)

- The TCB lists the instruction-set semantics' faithfulness, the enter stub,
  the code process, and the OS's mapping and protections.
- The README states which ops are proven, per instruction set, and which
  platforms run the JIT.

## Order of work

J.0 → J.1 (phase-7.md, 7.4 and 7.5) → J.2 → J.3 and J.4 in parallel →
J.5 → J.6 (x86-64 first: its validator is the harder one and its runners
are CI's main ones) → J.7 and J.8 → J.9 → J.10 → J.11 → J.12.

J.3 to J.6 need nothing from Phase 7 except J.1's choices, so they can start
while the parser and the GC are built. Nothing generated runs before its
validator is at tier 2.

## Risks

- **x86-64's semantics is large, and its two public formal models may share
  ancestry.** This is the assumption the safety claim rests on. Mitigations:
  - keep the subset small, with canonical encodings only;
  - the two formal models are not independent (J.2), so the second
    transcription comes from Intel's SDM, written by a different session
    (J.3's note);
  - hardware differential tests on two OSes;
  - a decoder differential over every accepted encoding.
- **The code process is new trusted code with a powerful handle.** It is
  kept to: receive bytes, run `clazel-codecheck`, map. It has no other
  input, and its tests include a renderer that sends hostile blobs.
- **The validator's recognizable sequences constrain the back ends.** That is
  accepted for a baseline tier. An optimizing tier needs a
  certificate-checking validator or translation validation.
- **Exit-based runtime calls cost an exit and an entry per slow op.** They
  are measured, and the fix is a wider fast path, not calling Rust from
  generated code.
- **Phase 7's choices slip.** Without J.1's constraints, the JIT needs
  deoptimization metadata and stack maps, and the plan grows.

## Looking ahead

- **WebAssembly:** `clazel-wasm`, holding a Wasm decoder and validator (our
  own parser, rule 8), with Wasm → LIR proven against a Verus transcription
  of the Wasm spec (WasmCert-Coq and WasmCert-Isabelle as independent
  sources). It reuses both back ends, both validators, the enter stub, the
  code process and the sandbox changes:
  - linear memory is a region;
  - `memory.grow`, host calls and traps are exits.
- **Linux aarch64 and Windows arm64:** the same crates. They need CI runners
  for hardware tests and the Windows arm64 ABI in the enter stub.
- **An optimizing tier:** speculation with deoptimization to the shared
  frame layout, and register allocation, each needing translation
  validation or a certificate-checking validator. This is research-grade,
  and is not promised.
